# Project notes

## Code style

- **No explanatory comments anywhere** — TS, templates, SCSS, migrations. What is worth remembering across sessions goes into this file; a note to the reviewer goes into the commit message. `TODO`/`FIXME` and tool directives (`@ts-ignore`, eslint) are fine. Keep this file compact.
- **Injected dependencies:** services carry the `Service` suffix (`private notificationsService: NotificationsService`), repositories the full entity name without it (`private notificationSettings: NotificationSettingsRepository`).
- **Prettier formats the repo**: `./backend/node_modules/.bin/prettier --write .` from the root (`.prettierrc.yml`: tabs, width 120). `.prettierignore` holds `!old`, `frontend/src/sdk`, `frontend/src/assets/lib`, `backend/assets` and `CHANGELOG.md` out of it.
- `!old/` is the retired server kept for reference — never edit it.

## Commits & changelog

- **Conventional Commits** (`type(scope): description`), enforced by commitlint. **Description in Czech**, `type`/`scope` in English: the visitor-facing changelog takes subjects **verbatim**.
- **Pick the type for the changelog reader**: `feat` only for a **notable** new feature (a new page, workflow or capability a user would notice) — not for every small addition; `patch` for an improvement of an existing feature (a new column, button, filter, tweak); `fix` for a bug fix. Other types as usual.
- **Squash a feature branch into one commit before merging** (`feat(scope): …` with every `Closes #…` in its body), so the feature shows up as one changelog entry instead of drowning among its work-in-progress commits. Separate `fix`/`patch` commits riding the branch may stay separate. **Don't squash if another branch depends on these commits** — that branch would lose them (its history no longer matches the squashed one).
- **The repo forbids GitHub squash merges** (405), so squash locally and merge the PR as a merge commit. **Squash against the merge base, never `git reset --soft origin/master`**: once master has moved, the soft reset keeps the branch's old tree, so the commit silently reverts everything merged since. Use `git reset --soft $(git merge-base HEAD origin/master)`, commit, then `git rebase origin/master`, and check `git diff --stat origin/master` lists only the branch's own files before force-pushing.
- **An issue reaches the changelog only if the commit itself references it** — `Closes #123` (also `Fixes`/`Resolves`/`Refs`) in the commit body, or `(#123)` in the subject. PR bodies are not git history; merges are skipped (`--no-merges`).
- `scripts/generate-changelog.mjs` **prepends** the new version's section to `CHANGELOG.md`, so older sections survive edits. One flat list per version, each entry led by its type's gitmoji (`feat` ✨, `patch` 🚸, `fix` 🐛, `style` 🎨, `perf` ⚡️, `refactor` ♻️, `docs` 📝, `test` ✅, `build` 📦️, `ci` 👷, `revert` ⏪️, `chore` 🔧, and last ❓ for non-conventional subjects, taken whole). A non-conventional subject repeating a typed commit's description merges into that entry. Served at `GET /api/changelog`; the version in the menu opens it.
- Each entry links to its commit and ends with its authors' **avatars**: author linked to GitHub, committer (usually Claude) tucked 60 % behind — no link, one shared tooltip ("Kopec a Claude"); commits committed by GitHub's own web UI show the author alone. Accounts resolve from GitHub no-reply emails, else `GET /repos/:o/:r/commits/:sha` (needs `GITHUB_TOKEN` and the commit pushed); no account → initials circle, a failed lookup costs only the avatar. `--no-authors` skips the API. Markup hangs off `changelog-credit`/`-author`/`-committer`/`-avatar` in `changelog-modal.component.scss`; `ChangelogLinksPipe` links `#123` and opens everything in a new tab. Pre-2023 sections came from the legacy `bosancz/bosan.cz` repo — commit links, no `#nnn`.
- Released sections are never regenerated, so changed markup needs `--backfill` (re-renders only each entry's gitmoji and credit, idempotent, matches by commit link so the hand-written `v4.0.0` entry stays untouched). `--backfill-other` appends the ❓ entries missing from each tag range (needs `git fetch --unshallow --tags`, idempotent, skips hand-written sections).
- **Both releases generate the changelog in the build job.** `build.yml` runs the generator before `docker build` whenever `changelog-version` is set; `changelog-branch` decides whether the file is kept. PRODUCTION passes `vN.N.N` + `changelog-branch: master` → committed and pushed **after** the image is published (a failed build must not record a version that never shipped), and `tag.yml` tags that commit. NEXT passes `NEXT-<short sha>` and no branch → the section lives only inside the image. The range is always "since the last `v*` tag".
- **The generator also writes `release-issues.json`** next to `CHANGELOG.md` — `{ version, date, repo, issues: [{ number, version, text }] }`, **cumulative**: every issue any section has ever recorded, re-read out of the rendered markdown after the prepend, so a release the running container never booted (two releases in quick succession) still notifies its reporters. Per issue it keeps the **earliest** version that carried it, sections being newest-first. Gitignored and never committed — `build.yml` stages only `CHANGELOG.md` — it reaches the image through the Dockerfile's `COPY release-issues.jso[n]`, the glob keeping a build without the generator working.

## Dev workflow

- **Never start a second dev server, or run `ng build`/`npm run build`, while one is already running.** Root `npm run dev` runs frontend + backend via `concurrently` and tees to `dev.log` (gitignored, `[FE]`/`[BE]` prefixes, raw ANSI). Verify your change by reading it (`tail -n 80 dev.log`); an error there may be another agent's in-flight change.
- **A missing or stale `dev.log` means no server is running** — you are in a fresh sandbox and are expected to start one, not to ship unverified.
  - **Angular needs Node 24**; the sandbox default (22.x) fails every `ng` command on the engines check. `nvm install 24` (`NVM_DIR=/opt/nvm`).
  - `npm ci` works in `frontend/` and `backend/`. Do **not** run the root `npm ci` — `scripts/install.sh` also builds the backend and runs migrations, so it needs a database. Don't commit lockfile churn from `npm install`.
  - Frontend-only change: `cd frontend && npm ci && npm run dev`. Backend change or the full root `npm run dev`: bring up Postgres and Redis first (below).
- **Whenever you run the web app to test a change, take a screenshot of the affected page and show it to the user** (Playwright + preinstalled Chromium, log in as a seed user, `SendUserFile`). Keep screenshots in the scratchpad, never commit them.
- **`.mcp.json` registers the Angular CLI MCP server** (`npx -y @angular/cli mcp`) — docs/best-practices plus workspace tools, run from the repo root, Node 24 like every `ng` command; its `devserver_start` falls under the one-server rule.

## Testovací data

- `npm run cli seed` (backend) naplní databázi vzorovými daty v hobitím duchu — `src/seed/`: uživatelé `bilbo` (admin), `vedouci`, `instruktor`, `program` a `pokladnik` — všichni s heslem z `SEED_PASSWORD` (bez té proměnné seed odmítne běžet) a s členem v Klubu přátel (`Bilbo`, `Beorn (vedoucí)`, `Elrond (instruktor)`, `Gandalf (správce programu)`, `Glóin (pokladník)` — přezdívka nese postavu i roli), takže mají i odvozenou roli vedoucího; oddíly Trpaslíci, Nepřátelé a Klub přátel, členové, budoucí akce podle typů a album s fotkami. Data jsou v `seed/data/seed-data.ts`. Akce se počítají od nejbližší soboty podle `schedule` (víkend so–ne, prodloužený víkend pá–ne, týden so–so) a `weeks`, takže padnou vždy na správné dny v týdnu a do budoucna; akce bez vedoucích může být jen `draft`, protože ji nemá kdo podat ke schválení — hlídá to `assertSeedEventStatuses()` a seed na nekonzistentních datech spadne dřív, než začne zapisovat. Seed proto u svých akcí nuluje i `statusNote` a značky odeslané ohlášky a vyúčtování, aby po změně statusu v datech nezůstaly viset z předchozího běhu. Fotky alba jsou soubory v `backend/assets/seed/photos` (assety se kopírují do image, cesta je relativní ke cwd jako u ostatních assetů) a seed je ukládá přes `PhotosFilesService.savePhotoFiles()`, takže vzniknou i náhledy v `DATA_DIR`.
- Příkaz je **idempotentní** — záznamy hledá podle přirozeného klíče (login / přezdívka / název) a aktualizuje je; kontakty, účastníky a útraty seedovaných záznamů přepisuje. Nic jiného v databázi nemaže, takže se dá pouštět i na prostředí s importovanými daty.
- **Kam se smí seedovat, rozhoduje značka v databázi** — `ALTER DATABASE <db> SET app.environment = 'test'` (resp. `'production'`). Bez značky příkaz odmítne běžet (i ve vývoji) a vypíše hotové SQL i to, že jde použít `--force`; databáze označená jako produkční se odmítne vždy, ani `--force` nepomůže. Značku nepřenáší `pg_dump` (jen `pg_dumpall`), takže obnova dat z produkčního dumpu do testovací databáze o ni nepřijde a špatně nasměrovaný `DB_HOST` seed zastaví.
- `npm run cli reset-db` zahodí schéma (`DROP SCHEMA ... CASCADE`) a spustí všechny migrace od začátku, s `--seed` rovnou naplní i testovací data; řídí se stejnou značkou. Rozšíření (`postgis`, `cube`, `unaccent`), kolaci i konfiguraci fulltextu vytvářejí samy migrace, značka `app.environment` visí na databázi, ne na schématu — po resetu tedy nic nechybí. Se schématem ale padnou i rozšíření v něm a `CREATE EXTENSION postgis` smí jen superuser (`cube`/`unaccent` jsou trusted), takže příkaz předem odmítne drop na nesuperuserovém spojení, aby databázi nenechal rozbitou uprostřed migrací. V kontejneru je to jediná cesta: `npm run migrations:*` jedou přes `ts-node`, který je devDependency a v image chybí.
- `SEED_ON_START=true` naplní data při každém startu aplikace (po migracích, `main.ts`) — tahle cesta `--force` nezná, bez značky `test` nebo bez `SEED_PASSWORD` se jen přeskočí s chybou v logu.

## Frontend SDK

- `frontend/src/sdk` is generated from the backend's OpenAPI spec — never hand-edit `api.ts`. After changing a backend controller/DTO run `npm run generate:sdk` from `frontend/` (reads `http://127.0.0.1:3000/api/openapi-json`, so the backend must be up). ## User settings

- **`User.settings` is an opaque `jsonb` blob owned by the frontend** — the backend never looks inside it. `GET /account/settings` and `PUT /account/settings` (whole object, `{ settings: … }`, `@IsObject()` only) are the only way in; the column is `select: false`, so it never rides along in `getMe` or the users list. Unknown keys survive a round trip untouched.
- Frontend goes through `UserSettingsService` (`core/services`): `watch(key)` returns a signal, `set(key, value)` writes through to `localStorage.userSettings` (instant, survives the reload before the API answers) and PUTs the whole object; requests are queued so they cannot overtake each other.
- **Only the keys in `PROPAGATED_SETTINGS` follow a change made in another tab** — just `darkMode`. Everything else is a per-tab working state that is still _saved_ for the next load: two tabs may show different columns or a different album view at once. The service keeps `stored` (what is persisted) apart from `pinned` (what this tab insists on showing), the view being `{ ...stored, ...pinned }`; an external change pins whatever the tab currently shows for the non-propagating keys before adopting the new `stored`. It pins the keys the tab has **watched**, not the keys already present — pinning only what `stored` happened to contain let the very first write of a key through to every other tab; pinning `undefined` for a watched-but-unset key keeps that tab on its defaults, while a tab that never watched the key adopts the new value when it later opens that page. The receiving tab never PUTs the echo back, and writes build on `stored`, so a tab holding an old view cannot push it back over another tab's. Whole keys are last-write-wins, so the last tab to touch `membersListColumns` defines the saved default.
- **`LocalStorageService.watchExternal()` sees only other tabs' writes**; `watch()` also fires for this tab's own `set()` and emits the current value on subscribe. Its `storage` handler parses `newValue` — it used to hand subscribers the raw JSON string on the cross-tab path and the parsed value on the same-tab one, so a cross-tab `false` arrived as truthy `"false"`. On login it loads from the server, but an **empty** server object with a non-empty local one is pushed up instead — that migrates the pre-existing `isDarkMode` / `albumsListView` keys, which `readCache()` still reads on first run.
- Persisted so far: `darkMode` (`DarkModeService`, injected in `AppComponent` so the theme applies before the sidebar exists), `albumsListView` and `membersListColumns`.
- **The members list merges its saved columns over `MEMBERS_LIST_COLUMNS`**, so a new column takes its default and a removed one drops out. The write goes to the settings only; an `effect` on the watched signal applies it, which is also what picks up the server's copy arriving after the first paint (and reloads the list when a contact column appears). That effect reads `viewSelections` for the previous state and writes it, so the read is wrapped in `untracked()` — without it the effect retriggers itself and hangs the page.

## Public API (bosan.cz)

- The iCalendar feed is `GET /api/public/program/ical` (`ProgramIcalService`, `ical-generator`). `ProgramIcalLegacyController` keeps the old server's `/api/program/ical` alive — deprecated in OpenAPI, same body. Never drop it without warning: ICS subscriptions are set-and-forget.
- Events are **all-day**: `DTEND` is exclusive (`dateTill + 1 day`) and the calendar deliberately sets **no** timezone (with one, `ical-generator` renders `DTSTAMP` as floating local time, which is invalid; the Luxon values carry `Europe/Prague` themselves). `timeFrom`/`timeTill` are free text ("ráno") and are never parsed.
- Cancelled events stay in the feed as `STATUS:CANCELLED` with a `Zrušeno: ` summary prefix. `UID` is `event-<id>@bosan.cz`, stable so clients update instead of duplicating. Window: `ICAL_DAYS_BACK` (30) back, unbounded forward; `EventsRepository.getPublicProgramIcal()` skips the 100-row cap of the JSON program endpoint.
- bosan.cz resolves the feed URL from the API root's `_links` (`program:ical`), falling back to a hardcoded URL — the hardcoded one going stale is what broke this originally (#352).

## Event statuses

- **`EventStates` (`event.entity.ts`) is `draft`, `pending`, `rejected`, `public`, `cancelled`.** `rejected` was dropped from the DB enum in 2023 (`1682264978418`) and reintroduced by `EventStatusRejected1787131906960`, so **"Vrátit k úpravám" (`POST /events/:eventId/reject`) sets `rejected`, not `draft`** — a returned event is distinguishable from one never submitted. That migration's `down()` maps `rejected` back to `draft` before narrowing the enum, or the cast fails.
- A `rejected` event is back in the leader's hands: `EventSubmitPermission` and `EventPublishPermission` treat it like `draft` (`events.acl.ts`). `POST /events/:eventId/unpublish` still returns to `draft` — removing from the programme is not a rejection. Nothing else branches on it; the public programme and iCal feed only match `public`/`cancelled`. `EventStatuses` (frontend `core/config/event-statuses.ts`) also carries `finalized`, which no backend code sets, so code mapping over statuses must tolerate it; `GET /events/statuses` returns the statuses actually present, so the list filter picks up new ones itself.
- **The announcement and the accounting are handed in outside the system**, so `Event.announcementSentAt`/`accountingSentAt` only record that someone marked them sent — `POST/DELETE /events/:eventId/announcement/sent` and `/accounting/sent`, applicable only on a `public` event, the DELETE undoing a mistaken click; permissions inherit `EventEditPermission`.
- `bo-event-progress` (event view, between header and content) always shows five points: příprava / schvalování / program, "Ohláška" ("Ohláška odeslána" once marked) and "Uzavřená n/3" — filled up to the active one, grey until reached. **Each step carries its own accent**: `--accent` for its dot and the rail leading into it, `--accent-out` (the next step's accent) for the trailing segment, so the whole line between two dots takes the colour of the dot it leads into. Points 1–3 take the status accent — `EventStatuses[status].color`, except `draft`, which is grey (`EventStatuses.draft.color`) without leaders and orange with them, a leaderless draft having nothing in progress yet. **`rejected` sits in point 1**, not 2 — it is back in the leader's hands — and labels it "Vrácená k úpravám"; point 2 reads "Schválena" once past it (`PAST_STEP_LABELS`). A `statusNote` adds a chat icon opening an `ion-popover` — popover content renders outside view encapsulation, so its styles are `::ng-deep`, as in `statistics-card-top-leaders`.
- **Point 5 counts all three closure items but only two of them gate it** — vyúčtování and report carry `EventClosureItem.required`; the gallery counts into `n/3` yet never blocks, so "Uzavřená 2/3" is a legitimately finished event. **Point 5 only lights up once there is something to close**: after the announcement is marked it stays grey while the event is still running (`dateTill` not yet past) and nothing required is done, so the highlight rests on point 4; from the day after `dateTill` it goes orange (`EventStatuses.pending.color`), and both required items done turn it green (`EventStatuses.public.color`) whenever that happens, even before the event ends.
- The whole step block is the click target (tinted hover on the label text) and opens a centred dialog via `ModalService.componentModal` like every other modal: `EventAnnouncementModalComponent` and `EventClosureModalComponent`, checkbox forms extending `InputModalComponent`. Closure lists accounting (the one tickable checkbox), report (derived from `event.report`) and gallery (from `event.album`: missing / `draft` / `public` — `getEvent()` joins it), the derived two disabled and the gallery marked "Nepovinné". The component calls the API on the modal result and emits `(change)` so `event-view` reloads.
- **The ŠÁN dialog chrome lives in `bo-modal-layout`, so every modal inherits it** — heading in the body font (the display font is reserved for headlines) with a yellow accent bar (`::after` on `.title`, keeping the `.title:empty` rule working for title-less sheets), brand paddings and footer border. Projected headings carry the caller's scope, so they are restyled via `::ng-deep` and inherit their size from `.title` — the changelog's `h1 { font-size: inherit }` depends on that. The card (radius, shadow, blue-tinted backdrop) is on `ion-modal.dialog`; `dialog-brand` only pins the width of the two event dialogs. Their row/button styles are in `src/styles/_brand-modal.scss`, tokens on `:host` plus a `:host-context(body.dark)` block so the handoff's light values don't break dark mode.
- **Ionic puts the `ion-page` class on the modal component's own host**, so the dialog's height chain runs `ion-modal` → that host → `bo-modal-layout`. `_brand-modal.scss` must therefore keep `:host` a `display: flex` column with `min-height: 0`, `max-height: 100%` and `overflow: hidden` — with `display: block` the layout's `flex: 0 1 auto` was inert, `.content` never scrolled and a tall form (kontakt na rodiče) pushed the footer buttons outside the 90dvh cap (#464). `ion-modal.dialog > .ion-page` adds the cap and `overflow: hidden`; `bo-modal-layout` tightens its paddings under 576 px.
- **Bootstrap is loaded globally, so `.modal-header`/`.modal-body`/`.modal-footer` are taken** — its rules centred the title. Component classes there are prefixed `bm-`.
- **Správce programu (`program`) vede akci po obsahové stránce, ne po účastnické.** `EventEditPermission` mu dává `program: true`, takže edituje název, popis, sraz, oddíly, přihlášku i report. Vedoucí přidává přes vlastní routu `PUT /events/:eventId/leaders/:memberId` (`addEventLeader`, upsert — z účastníka udělá vedoucího) s `EventLeaderCreatePermission`, která dědí `EventEditPermission`; funguje i na akci bez vedoucích, takže si ji nemusí nejdřív vzít (`leadEvent` zůstává pro vedoucí). Odebírá se pořád přes `DELETE …/attendees/:memberId` — `EventAttendeeEditPermission` (a z ní děděná delete) k tomu pouští `program` jen u řádku s `type === "leader"`, takže účastníky ani výdaje nepřidá ani neodebere. Ve frontendu tlačítka rozlišuje `canAddLeader()` / `canAddAttendee()` (`event-attendees`); dva linky = dvě routy, jedna routa nese v `_links` jen jeden.
- **Pořadí vedoucích drží `EventAttendee.position`** (#507) — první vedoucí je hlavní kontakt pro rodiče, takže ho bosan.cz musí ukazovat první (vykresluje `leaders` z API tak, jak přijdou). Všechny cesty, které plní `event.leaders` (seznam, detail, veřejný program, iCal, ohláška, vyúčtování, přihláška), řadí přes `getEventLeaders()` (`models/events/helpers/event-leaders.ts`): `position` vzestupně, bez pozice nakonec, pak přezdívka — `leftJoin` sám žádné pořadí nezaručuje. Přetažením v záložce Lidé se volá `PUT /events/:eventId/leaders` (`{ memberIds }`, `EventLeadersOrderPermission` dědí `EventEditPermission`); nově přidaný nebo povýšený vedoucí i ten ponížený na účastníka dostane `position: null`.
- **Report patří vedoucím akce, ne správci programu.** `EventReportEditPermission` má vlastní `vedouci: isMyEvent` (nedědí `EventEditPermission`) a visí na `PUT /events/:eventId/report` — jediné cestě, jak report uložit: `EventUpdateBody` pole `report` **nemá**, takže `PATCH /events/:eventId` s ním skončí na 400. Fotogalerie zůstává na `updateEvent` a připojuje se přes `PATCH /albums/:albumId`, tam se práva zatím neřešila.
- **Tlačítko bez práv se nezhasíná, ale zakazuje** — `[disabled]` + `[boTooltip]="…nemáš oprávnění."` (text `noPermissionText`, jako v `bo-action-buttons`). `ion-button.bo-tooltip.button-disabled` v `styles/ionic.scss` mu vrací `pointer-events`, takže tooltip najede i na zakázaném tlačítku.
- **Karta akce (`event-card`) je v záložce Info vidět v každé šířce** — `order-first order-xl-last`, na mobilu tedy nad seznamem údajů. Je to jediné místo, kde je bez rozkliknutí vidět „Vede …“ (#415).
- **Řeka a kilometry na vodě** (`Event.river`, `waterKm`) se edituje v záložce Info. Řeka je volný text — `RiverSelectModalComponent` nabízí `POPULAR_RIVERS` nahoře a celý `RIVERS` abecedně (`core/config/rivers.ts`, řazeno `Intl.Collator("cs")`), a dokud hledaný text není přesně název řeky, nabízí ho i jako vlastní hodnotu (název může být součástí jiného). `waterKm` je `numeric`, takže ho entita převádí transformerem na číslo (pg vrací string).
- **A modal's "can I edit this" flag must read the persisted value, not its own checkbox signal** — `unmarkX.allowed` is false while `xSentAt` is null, so deriving it from the checkbox disables the save button the instant the box is ticked.

## Seznam akcí

- **Náhled akce po najetí myší (`event-hover-preview`) se řídí `PointerEvent.pointerType`, ne media dotazy.** Původní `@media (hover: none), (pointer: coarse)` (ani varianta s `any-hover`/`any-pointer`) nefunguje: prohlížeč umí své ukazovátko hlásit špatně — Vivaldi na notebooku s dotykovým displejem hlásil `any-pointer: fine: false`, tedy „žádná myš“, dokud ho uživatel nerestartoval. Handlery jsou proto `pointerover`/`pointermove` a pouštějí dál jen `mouse` a `pen`; dotyk se odfiltruje sám a `pointerdown` náhled zavírá. Náhled se ukazuje s prodlevou 500 ms (`previewDelayMs`). Je to sdílená `bo-event-hover-preview` (`shared/components`) — hostitel jí předá `events`, na obalu seznamu volá `hover()`/`clear()` z pointer událostí, řádky nesou `id="event-<id>"` a v `ionViewWillLeave`/`WillEnter` ji `pause()`/`resume()`; používá ji seznam akcí a řádkové sloupce `/program` (#536), karty Ke schválení ne, ty obsah náhledu už ukazují.
- **`PlatformService.isMobile` je `is("android") || is("ios")`, ne Ionicovo `is("mobile")`** — to je pouhé `matchMedia('(any-pointer:coarse)')`, tedy přesně ten nespolehlivý dotaz výše (notebook s dotykovým displejem se hlásí jako mobil). Ionic si výsledek cachuje do `win.Ionic.platforms` a `isMobile`/`isIos` nemají trigger, takže se po startu nemění — čte se z nich `.value` (na rozdíl od `isLg`/`isPortrait`, které jedou přes `platform.resize`). Řídí se tím automatické otevření výběru fotek (`photos-upload`) a tlačítko „Zaplatit v bance“ (`member-payment`), které sdílí QR do bankovní aplikace přes Web Share — to má dnes i desktop, ale bez banky za ním.

## Pokladna

- **Pokladníka dělá role `pokladnik`** (#456) — aby správa příspěvků nevyžadovala admina. Přidává dvě práva: `MemberMembershipUpdatePermission` (jediná cesta, jak se zapisuje zaplacený příspěvek — status, datum, částka i poznámka) a `PaymentSettingsUpdatePermission` (číslo účtu a výše příspěvku). Nic dalšího nedává: na seznam členů se pořád dostane jen přes odvozenou roli `vedouci`, takže pokladník musí být zároveň aktivní člen (jako `program` a `revizor`, které se taky jen přičítají). **Viditelnost stránek řídí role uživatele, ne `_links`** — `UserService.hasRole()` (admin projde vždy) a `roleGuard()` na routě: `/prispevky` (+ `/prispevky/platebni-udaje`, `features/treasurer`) pro `pokladnik`, `/program` pro `program`, `/admin` jen pro `admin`. Příspěvky a Program jsou v hlavním menu sidebaru i v dlaždicích na homepagi, Administrace zůstává v účtové části menu. **Oddíl** (sidebar i dlaždice, ta i offline vedle Databáze — offline odpovědi umí `GET /groups` i `/groups/:id`) vede na oddíl člena napojeného na účet (`UserService.myGroupId` → `group: 'code'`) a bez člena chybí. Stránka oddílu je samostatný modul `features/groups` s URL podle **`Group.shortName`, který je unikátní** (`/oddily/:group`, `/oddily/:group/upravit`; duplicita při vytvoření/úpravě = 409). Zkratku na id překládá předstažený seznam v core `GroupsService` (ten, ze kterého čte `GroupPipe`) — `getGroupByShortName()`/`getGroupById()`, při nenalezení seznam jednou znovu načte; po úpravě oddílu se volá `reload()`. Seznam a smazané oddíly zůstaly v `/databaze`, staré `/databaze/oddily/:id` přesměrovává guard. Tlačítka uvnitř stránek (u příspěvku `_links.updateMemberMembership`) se dál řídí odkazy.
- **Na dotykovém ovládání je pilulka zaplaceno/nezaplaceno zamčená** (#472) — přepínač „Povolit úpravy“ vpravo v řádku se souhrnem (Platících / Vybráno) ji odemkne. Zamčená pilulka **zůstává tlačítkem** (bez rámečku, `treasurer-membership-pill` sám vs. s `-toggle`, `aria-disabled`), takže ťuknutí nezmizí do prázdna: `toggleMembership()` místo překlopení ukáže toast s tlačítkem „Odemknout“ (#477) — na dotyku není tooltip, ze kterého by se zámek dal přečíst. Gate je `canEdit()` = bez dotyku nebo odemčeno, hlídá ho `toggleMembership()`, ne jen šablona; **tužky u částky a poznámky zámek nedrží** — ty jdou přes `canEditMembership()` a otevírají dialog, takže omyl nic nepřepíše. Zámek je stav komponenty, takže se při každém otevření stránky vrací zpátky — persistovat ho by ochranu zrušilo.
- **Export do XLSX jede přes stejnou routu jako seznam, takže musí dostat i `sort`/`order`** (#468) — bez nich spadne na fallback `sort_nickname ASC` a sešit vyjde v jiném pořadí, než co je na obrazovce. V pokladně je obojí součástí `filterParams()`, které sdílí seznam i export (`loadMembers` je proto už nepřidává); seznam členů si je skládá ve svém `export()`. Sloupce se jménem jsou v obou sešitech dva (`Jméno` = `firstName`, `Příjmení` = `lastName`), aby se dal sešit přetřídit podle příjmení.
- **Pruh se souhrnem je pod 576 px sloupec, ne řádek** (#481) — tři věci se na šířku telefonu nevejdou a přepínač „Povolit úpravy“ se zalomil na vlastní řádek, kde ho `margin-inline-start: auto` odsunulo doprava, k ničemu nezarovnaný. V `@media (max-width: 575.98px)` je z něj celý řádek pruhu (`flex-basis: 100%`, `justify="space-between"` na `ion-toggle`) oddělený linkou; vnitřní odsazení pruhu tam zároveň klesá z 32 px na 16 px, které používá vyhledávání i seznam pod ním, takže celý levý okraj stránky sedí na jedné lince.
- **Výzva k platbě e-mailem jde jen na výchozí kontakt** (#488) — `member-payment` bere e-maily z `getDefaultContact()` (padá na první kontakt), ne ze všech kontaktů člena.
- **Dotyk pozná `PlatformService.isTouch`** (signál): `navigator.maxTouchPoints > 0` plus globální `pointerdown` s `pointerType === "touch"`, protože media dotazy lžou (viz _Seznam akcí_) a `isMobile` je jen android/ios — hlásící se notebook s dotykovým displejem je přesně ten případ z #472. Myš přepínač nikdy neuvidí.
- **Datum platby je řaditelný sloupec** (#484) — `sort=paidOn`; `MembersRepository` ho bere z poddotazu `membership_payments.paid_on` za `membershipYear`, takže se řadí podle roku na obrazovce. **Prázdná data jdou v obou směrech nakonec** (nezaplacený příspěvek žádné datum nemá, zaplacený ho mít nemusí) — `applySort` proto umí u sloupce i `nulls`. Vzestupně/sestupně se přepíná jako u každého jiného sloupce: kliknutím do hlavičky na desktopu, šipkou u výběru řazení na mobilu.
- **Jméno a příjmení jsou dva sloupce** (#484) — v pokladně i v seznamu členů, oba ve výchozím stavu zapnuté a oba řaditelné: `sort=firstName` (křestní, pak příjmení) a `sort=lastName` (příjmení, pak křestní — to, co dělával klíč `name`). `name` v repozitáři zůstává jako alias na `lastName`, protože ho pořád používá `bo-group-members` a nesou ho uložená nastavení i odkazy; z `membersListColumns` starý klíč vypadne sám, seznam se skládá přes `MEMBERS_LIST_COLUMNS`.
- **Každé řazení kromě přezdívky dostane `sort_nickname ASC` jako druhotné kritérium** — shodné hodnoty (oddíl, datum platby, zaplaceno/nezaplaceno) se jinak mezi stránkami přerovnají a nekonečné scrollování řádky přeskakuje nebo opakuje.

## People picker

- **`MemberSelectorModalComponent` is the only picker on people.** It wraps `bo-modal-layout` like every other modal — title/subtitle + ✕ in the title slot, sticky search and group chips above the scrolling list, count and buttons in the footer (design handoff "Výběr lidí", #357). `dialog-picker` pins it to 560 px / 720 px.
- Ionic assigns `componentProps` as plain properties, so `selectedIds` is a **`Signal<number[]>` owned by the caller** — that is what repaints the checked state when the underlying list changes. Without it the picker is single-select: no checkboxes, no count, "Zrušit", closes on the first pick (`users-view`).
- With `keepOpenAfterSelect` the modal stays open, the button reads "Hotovo" (everything is already saved) and `onSelect`/`onDeselect`/`onClearAll` may be async — the row shows a spinner and ignores further clicks meanwhile. `event-attendees` adds, removes and clears through it. **Losing a leader is always confirmed** (#453): the list's delete button, unchecking one in the picker, clearing them all, and picking a leader in the attendee picker — that one goes through `updateEventAttendee`, which silently demotes them, so it asks before the call.
- **„Přidat „…“ jako nového člena“** se v pickeru nabízí jen s `allowCreate: true` (účastníci akce, přiřazení obličeje, propojení účtu — ne ve filtrech ani sloučení) a jen v prázdném výsledku hledání; otevře `MemberCreateModalComponent` s přezdívkou z hledání, oddílem z čipu a rolemi zúženými na `roles` pickeru (`allowedRoles`), člena vytvoří a rovnou ho vybere přes `toggleMember()` — tedy i přes `onSelect`. Jen s `_links.createMember` a jen když picker členy načítá sám (ne nad předaným `members`).
- **Klávesnice**: šipky ve vyhledávání posouvají zvýraznění (`activeIndex`, `linkedSignal` nad `filteredMembers`, takže se změnou výsledků skočí na první), Enter zvýrazněného vybere (`toggleMember()`), v prázdném výsledku nabídne vytvoření člena.
- **Filtering never touches the selection** — the footer count is the source of truth. Search is diacritics-insensitive substring over nickname + first/last name; group chips come from the groups actually present in the loaded list. Group tags tint the group's own colour (`rgba` + a fixed-lightness `hsl`, both themes as `--mp-tag-*` custom properties) instead of the solid badge used in lists.
- **Content projection ignores `slot=` on elements inside `@if`** — the footer must be projected unconditionally, with the branch inside it, or it silently lands in the default slot. The host also needs `display: flex; max-height: 100%`, or the list overflows past the footer instead of scrolling.

## Albums

- `GET /albums` returns each album's `coverPhoto` — the title photo, else the album's first photo (`PhotosRepository.getCoverPhotosByAlbums`, `DISTINCT ON`); the public gallery keeps its own title-photo-only lookup. `albums-list` has a table/grid segment toggle at the toolbar's right (choice in `localStorage.albumsListView`); the grid shows cover photos, and the pills over them get a solid backing because the dark theme's `--bo-*-tint` backgrounds are semi-transparent. `ion-segment` is `display: grid; grid-auto-columns: 1fr`, so a compact segment needs `grid-auto-columns: max-content` + `width: fit-content`.
- **Přibližování v prohlížeči fotek** (`bo-photos-edit`, #562) — vlastní pointer gesta, žádná knihovna: dvojí ťuknutí/dvojklik (2,5×), pinch, kolečko, `+`/`-`/`0`, tažení posouvá. Obrázek i vrstva obličejů jsou v `.zoom-stage` s `transform` (origin `0 0`), posun se ořezává podle `imageRect`; rámečky a popisky obličejů se dělí `--zoom`, aby nerostly. Jedno ťuknutí (ovládání, se zpožděním 300 ms kvůli dvojímu) platí jen bez přiblížení. **Rámečky obličejů gesta nepohlcují** — jdou stejnou cestou přes `onPointerDown` (viewer si bere pointer capture, takže `click` na rámeček nedorazí), jedno ťuknutí na rámeček (`data-face-id`) otevře menu obličeje po stejné prodlevě, dvojí přibližuje a pinch začatý na obličeji funguje; `(click)` rámečku reaguje jen na klávesnici (`detail === 0`). Po prvním přiblížení se přes `big` (1280 px) položí `original`.
- **Přepínání fotek je filmový pás** — `slides()` vykreslí předchozí, aktuální a další fotku (`track` podle id, takže soused se při přepnutí stane aktuálním **tím samým `<img>`**, bez znovunačtení), `.filmstrip` jede za prstem a po puštění (čtvrtina šířky nebo švih) dojede animací, pak `finishSlide()` přepne index a vynuluje posun. Šipky a tlačítka jedou stejnou animací. Protože už načtený soused nevystřelí `load`, `openPhoto()` měří obrázek přes `afterNextRender` a `clampZoom()` si ho při chybějícím `imageRect` změří sám — jinak přiblížení na nové fotce tiše spadlo na 1×.
- **EXIF je v `photos.exif`** (jsonb, `select: false`, `PhotoExif` v `schema/photo-exif.ts` — už rozparsované údaje: fotoaparát, objektiv, clona, čas, ISO, ohnisko, kompenzace, blesk, GPS; fotka bez EXIFu má objekt plný `null`, `NULL` = ještě nenačteno). Plní ho jen nahrání fotky a hromadně `npm run cli photos-exif` (`--all` přečte znovu i uložené) — **`GET /photos/:photoId/exif` jen čte uložené, při `NULL` vrací prázdný objekt a originál nikdy nečte** (tak je to domluvené). Zobrazuje ho postranní panel „Info“ v `bo-photos-edit` (na mobilu spodní polovina, klávesa I), otevřenost drží `UserSettings.photoInfoVisible` jako obličeje. `ion-toolbar` má `width: 100%`, takže při posunu `right` potřebuje i `width: auto`.
- **Fotky člena (záložka Fotky i `/galerie/nove-fotky`) jsou po albech** — `groupPhotosByAlbum()` (`helpers/album-photos.ts`). `getMemberPhotos()` proto řadí podle alba (`dateFrom DESC`, pak `id`) a uvnitř jako galerie (`order`, `timestamp`), takže stránkování přidává fotky jen do posledního alba a skupiny se netrhají.

## Kontakty na rodiče

- **`MemberContact.mobile` a `email` jsou `varchar[]`** (`NOT NULL DEFAULT '{}'`) — jeden kontakt může nést víc čísel i adres. Migrace `MemberContactsArraysAndDefault` převádí původní sloupce (`ARRAY[hodnota]`, prázdné na `{}`) a `down()` bere zpátky první prvek. Prázdné a bílé hodnoty ořezává DTO (`EnsureStringArray` v `helpers/validation.ts`), controller navíc dosazuje `[]`, takže odpověď pole vždy má.
- **Generovaný `search_vector` neumí `array_to_string`** — ta je v Postgresu `STABLE`, a generovaný sloupec chce `IMMUTABLE`. Migrace proto vytváří `immutable_array_to_string(text[], text)` (SQL, `IMMUTABLE`) a výraz spojuje pole `', '`; čárka je nutná, aby normalizace telefonů (mazání mezer mezi číslicemi) neslepila dvě čísla v jeden token. Změna výrazu se musí projevit i v `asExpression` entity.
- **`MemberContact.isDefault` označuje výchozí kontakt** — nejvýš jeden na člena: `MembersRepository` po zápisu s `isDefault: true` shodí příznak ostatním, jinak nic nedopočítává. Čtenáři berou `getDefaultMemberContact()` (`models/members/helpers/member-contacts.ts`, ve frontendu `DefaultContactPipe`), která **padá zpátky na první kontakt**, takže člen bez označeného kontaktu se chová jako dřív. `getContacts()` i `getMembers({ contacts: true })` řadí výchozí kontakt první.
- Formulář kontaktu je `MemberContactModalComponent` (`dialog-brand`, styly z `_brand-modal.scss` + vlastní `mc-*`) — původní `ion-alert` neuměl dynamická pole. Telefony a emaily se přidávají tlačítkem „+“ a přerovnávají táhlem (`ion-reorder-group`, které je ve výchozím stavu `disabled`; táhlo se ukazuje až od druhé hodnoty), validace (vztah, aspoň jeden kontakt) je uvnitř modalu. Na pořadí záleží — první číslo kontaktu jde do exportu. V kartě „Kontakty na rodiče“ nese výchozí kontakt pilulku „Výchozí“; sloupce seznamů členů (`firstTelephone`/`firstEmail`, popisky „Telefon/Email na rodiče“) ukazují výchozí kontakt a každou hodnotu na vlastním řádku — `td` má `white-space: nowrap`, takže spojené hodnoty přetékaly do vedlejšího sloupce.
- **`bo-group-missing-data` hlídá telefon a e-mail na rodiče zvlášť** — dvě položky („Telefon na rodiče“ `call-outline`, „E-mail na rodiče“ `mail-outline`), takže dítě s kontaktem bez e-mailu už neprojde jako vyplněné. Na rozdíl od sloupců seznamů se ptá **napříč všemi kontakty** (stačí telefon u jednoho a e-mail u druhého), ne jen výchozího; dítě bez kontaktů dostane obě položky.
- **Tlačítko „Napsat všem“ vedle nadpisu Účastníci** (`event-attendees`) skládá `mailto:` na **všechny lidi na akci**: u dětí e-maily výchozího kontaktu, u instruktorů a vedoucích `Member.email`. **Účastníci jsou příjemci, vedoucí akce jdou do kopie** (`?cc=`) — a když e-mail nemá žádný účastník, vedoucí se posunou do příjemců, aby pole „Komu“ nezůstalo prázdné. Adresu vybírá `getMemberEmails()` (`frontend/src/helpers/member-contacts.ts`, kam se z `DefaultContactPipe` přestěhoval i výběr výchozího kontaktu) a odduplikují se napříč oběma poli, takže rodič, který je zároveň vedoucí, dostane zprávu jednou. **Chybějící e-mail varuje, ale nezastaví** — když někdo e-mail nemá, tlačítko nenese `href` a kliknutí nejdřív otevře alert, který ty lidi vyjmenuje („Doplň ho v databázi.“) (`ModalService.confirmationModal`, „Napsat ostatním“ pak pustí `mailto:` přes `window.location`); nemá-li e-mail nikdo, je to jen hláška `alertModal` bez cesty dál. Nadpis i tlačítko jsou v `.list-header` s vlastními okraji (`16px 0 10px`) a `h3` uvnitř má nulové — vlastní horní okraj nadpisu jinak `align-items: center` odsadí, takže tlačítko sedí o 8 px výš; doprava ho tlačí `margin-inline-start: auto`. Pod 576 px zůstane z tlačítka jen ikona (skrytý `.mail-label`). Kontakty kvůli tomu joinuje i `EventsRepository.getEventAttendees()` — stejná práva jako seznam členů s kontakty (`vedouci`).

## Obličeje a worker (#452)

- **`worker/` je samostatný Python image** (`bosancz/interni-sekce-worker`) — **jeden kořenový `Dockerfile`, tři targety**: `app` (poslední stage, takže holý `docker build .` dá aplikaci), `worker` a `postgres`; `build.yml` bere vstup `target`, release workflowy mají joby `build-app` („Build APP“), `build-worker` („Build WORKER“) a `build-postgres` („Build POSTGRES“) a tag i deploy čekají na všechny pro úlohy mimo Node — zatím jen `detect-faces` (OpenCV Zoo YuNet + SFace, modely se stahují při buildu s kontrolou sha256). Nemá DB ani HTTP: s backendem mluví **jen přes Redis + BullMQ** (`bullmq` v Node i Pythonu, stejný formát). Fronta na typ úlohy `worker-<task>` (BullMQ nesnese `:` ve jménu fronty ani v `jobId`), výsledky jdou zpátky do `worker-results`. `WORKER_TASKS` (`*` nebo seznam) určuje, co instance dělá; všechny úlohy jdou přes jeden `asyncio.Lock`, takže instance zpracovává vždy jen jednu. Vlákna OpenCV = CPU limit kontejneru (`cpus:` v compose, čte cgroup), ladicí konstanty jsou v `worker/config.py`, ne v env.
- **Redis je povinný** — bez `REDIS_URL` API i CLI spadnou při startu (vyhazuje to factory `BullModule.forRootAsync` v `QueueModelModule`, `models/queues`, importovaném v `app.module` i `cli.module`), takže kód nikde neřeší, jestli Redis je: žádné `@Optional` služby ani záložní cesty. Migrace a `data-source.ts` Redis nepotřebují. Moduly s frontami si je jen registrují (`WorkerModelModule`, `NotificationsModelModule`).
- **Plánuje backend** (`models/worker`): BullMQ job scheduler `faces-enqueue` (`FACES_CRON`, výchozí 1:00 Europe/Prague) vloží `FACES_BATCH_SIZE` (300) fotek s `faces_detected_at IS NULL` **od nejnovějších**, `faces-stop` (`FACES_STOP_CRON`, 3:00) zbylé čekající úlohy zahodí — dojedou další noc. **Nahraná fotka se zařadí hned** (`PhotosController.createPhoto` → `enqueuePhotos()`, fire-and-forget, stejné `jobId`, takže se s dávkou nezdvojí) — noční dávka pak doplňuje jen to, co vypadlo (výpadek Redisu, zahozené ve 3:00, import). Ručně `npm run cli faces-enqueue -- --limit N`. Worker dostane cestu relativní k `DATA_DIR` (mountuje ho read-only) na `big` náhled; fotka mimo `DATA_DIR` shodí celou dávku.
- **Detekce jede ve více měřítkách** — YuNet obličej přes skoro celou fotku (portrét) na plném rozlišení nenajde, takže `detect()` pouští detektor i na zmenšené kopie (`FACES_LARGE_SCALES`, s černým okrajem `FACES_LARGE_PADDING`) a výsledky slučuje NMS. Migrace `PhotoFacesLargeFaces` po zavedení znovu zařadila fotky bez nalezeného obličeje.
- **Box obličeje jsou zlomky 0–1 orientovaného obrázku** (`x`, `y`, `width`, `height` v `photo_faces`), takže sedí na náhled i na originál po `sharp().rotate()`. Embedding je pgvector `vector(128)` (L2 normovaný, `FACE_DESCRIPTOR_DIMENSION`); kód, který ho čte do JS (`matchPhotos`), si ho v SQL převede `descriptor::real[]`, srovnání vzorů jde v SQL přes `-(a <#> b)` (= skalární součin). `photo_faces.photo_id` má index. Opakovaná detekce smaže jen obličeje s `assignment IS NULL` a nové, které překrývají zachovaný (IoU > 0,5), nevloží.
- **Automatické přiřazování** (`PhotoFacesMatchingService`, logika v `helpers/face-matching.ts`): `photo_faces.assignment` je `null` (nerozhodnuto), `auto` nebo `manual` — `manual` s členem je **vzor**, `manual` bez člena **zamítnutí** (automatika na něj už nesáhne). Porovnává se **jen se vzory**: skóre člena = max. skalární součin se všemi jeho vzory, přiřadí se při ≥ hranici (jednořádková tabulka `face_matching_settings`, výchozí 0,50 = `FACE_MATCH_THRESHOLD`; mění se na `/admin/fotky/prirazovani-obliceju` přes `PUT /face-detection/matching/settings`, které rovnou spustí celý přepočet), náskoku `FACE_MATCH_MARGIN` (0,05) před druhým a jistotě detekce ≥ `FACE_MATCH_MIN_DETECTION_SCORE` (0,90) — hodnoty z analýzy 10/2026, na fotce každý člen nejvýš jednou a nikdy člen ručně přiřazený na téže fotce; `auto` s lepším kandidátem se přepíše, nejisté se zruší. Zápisy jdou dávkově s podmínkou `assignment IS NULL OR 'auto'`, takže běh nikdy nepřepíše souběžné ruční rozhodnutí. Spouští to: výsledek detekce (ta fotka), `PATCH`/`DELETE` obličeje (vlastní fotka synchronně, zpětný průchod na pozadí s 2s debounce — jeden SQL scan přes všechny nové vzory), noční `faces-match` (`FACES_MATCH_CRON`, 3:05), `POST /face-detection/match` (202, na pozadí) a `npm run cli faces-match`. **Skóre počítá jen worker** (úloha `match-faces`, numpy po blocích `MATCH_FACES_BLOCK` = 2048 obličejů, `np.maximum.reduceat` přes vzory seřazené podle člena) — i pro jednu fotku po detekci či `PATCH`. `FaceMatchingWorkerService` uloží do Redisu (`worker-match-faces:<run>:…`, TTL 1 h, po běhu smaže) vzory jednou a obličeje po dávkách `PHOTOS_CHUNK` fotek jako surové `vector_send(descriptor)` bez 4bajtové hlavičky (big-endian float32, worker čte `>f4`), členy vzorů a dvojice (index obličeje, ručně přiřazený člen na téže fotce) pošle v datech úlohy a dostane zpátky nejlepšího a druhého kandidáta; rozhodování (`decideFaceMatches()`: hranice, náskok, jistota detekce, člen na fotce jednou) i zápisy zůstávají v Node. 96k × 3,9k: ~5 s (dřív ~110 s CPU v API), worker ~130 MB. **Výpočty workeru nemají záložní implementaci v Node** — bez živého workeru s `match-faces` (heartbeat) běh skončí chybou (`lastRun.error`, `matchPhoto()` ji jen zaloguje, `PATCH` projde) a obličeje se nepřiřadí. Výpočet testuje `face-matching-worker.spec.ts` přes Python workeru (`WORKER_PYTHON`, `worker/.venv`, nebo `python3` s numpy, jinak se přeskočí). Vlákna numpy omezuje `worker/__init__.py` (`OPENBLAS_NUM_THREADS` = CPU limit). Potvrzení v UI = `PATCH` se stejným `memberId`. **Kandidát pro ladění hranice**: každý běh zapíše u nerozhodnutých obličejů nejlepšího kandidáta i pod hranicí (`candidate_member_id`, `candidate_score`, `candidate_second_score`); ruční rozhodnutí je nepřepisuje (UPDATE jen `assignment IS NULL OR 'auto'`), takže u `manual` zůstane, co automatika navrhovala. `analyzeFaceMatching()` (`helpers/face-matching-analysis.ts`) z nich počítá přesnost podle hranice a navrhne nejnižší hranici s přesností ≥ 95 % (až od 50 rozhodnutí a 10 chybných kandidátů); nic se samo nemění, stránka nabízí „Použít návrh“. Stránka `/admin/fotky/prirazovani-obliceju` (`GET /face-detection/matching`) ukazuje stav a průběh přepočtu (stav drží `PhotoFacesMatchingService` v paměti procesu — CLI běh ho nevidí), návrh a tabulku; `/admin/fotky/obliceje` je jen detekce. **Karta „Kontrola obličejů“** (`bo-face-review-card`, na ≥ 1400 px pravý sloupec té stránky) bere po jednom obličeji z `GET /face-detection/review` — dvě nezávislé volby: `order` (`uncertain` = `auto` od nejnižšího `match_score`, `candidates` = nerozhodnuté s kandidátem od nejvyššího `candidate_score`, `random` = obojí náhodně, bez filtru i nerozhodnuté bez kandidáta) a volitelný `filter` (`leaders` / `children` podle role `vedouci` / `dite`, `member` + `memberId`), který u `auto` zužuje přiřazeného člena a u nerozhodnutých kandidáta; `order` je segmentový přepínač, `filter` pilulka s popoverem čipů (`filter-pill-chips-popover`; „Vybraný člen…“ otevírá výběr člena a otevřený popover blokuje klávesy); ukládá přes běžný `PATCH`/`DELETE` obličeje; po každém rozhodnutí přeskočí na další fotku — prohlédnuté fotky posílá v `excludePhotoIds` (posledních 300). Klávesy A/V/N/S. **„Zpět“ (Z / Ctrl+Z)** vrací rozhodnutí i přeskočení (historie posledních 50, smaže se změnou pořadí nebo filtru): rozhodnutí vrací `DELETE /photos/:photoId/faces/:faceId/assignment` (`resetPhotoFaceAssignment` — obličej zpátky na `assignment IS NULL` a hned `matchPhoto`, takže automatika obnoví případné `auto` přiřazení) a obličej se znovu načte přes `review?faceId=`. „Není to obličej“ vrátit nejde — smazaný obličej do historie nepatří.
- **Návrhy v modalu fotky**: klik na obličej bez člena v `bo-photos-edit` načte `GET /photos/:photoId/faces/:faceId/suggestions` (`PhotoFacesMatchingService.getSuggestions()`) — **počítá se v reálném čase** jedním SQL proti všem vzorům (`max` přes vzory člena, dva nejlepší členové, bez členů přiřazených jinde na téže fotce; ~40 ms na 96k obličejů) a výběr dělá `pickFaceSuggestions()` (≥ `FACE_SUGGESTION_MIN_SCORE` 0,36, druhý jen při náskoku < `FACE_SUGGESTION_MARGIN`). Uložený `candidate_*` slouží už jen analýze hranice. Kliknutí = běžný `PATCH` (ruční přiřazení).
- **Emoce**: worker pustí na stejný zarovnaný výřez 112×112 jako SFace i OpenCV Zoo FER (MobileFaceNet, `fer-2022july`) a ukládá `photo_faces.emotions` (jsonb, softmax sedmi tříd `angry/disgust/fearful/happy/neutral/sad/surprised`) a `emotion` (nejsilnější). Překrývá-li nová detekce přiřazený obličej, **aktualizuje se ten přiřazený** (id, člen i profilovka zůstanou), takže přepočet po změně modelu doplní data i jim. Nový model = migrace, která vynuluje `photos.faces_detected_at` (jako `PhotoFacesEmotions`). Frontend: `helpers/face-emotions.ts` (popisky, emoji); výběr profilovky řadí podle `happy`.
- Přiřazuje každý `vedouci` (`PATCH /photos/:photoId/faces/:faceId`; každé ruční rozhodnutí, i zamítnutí, zapíše `assigned_by_id` + `assigned_at`, automatika `assigned_by_id` nuluje), výřezy obličejů jsou líná cache `thumbs/faces/<faceId>.jpg`. **Profilová fotka je kopie**: `PUT /members/:memberId/profile-photo` vyřízne obličej z originálu do `members/<id>/profile_photo.jpg` (512 px), takže přežije smazání fotky; `profilePhotoFaceId` je jen zpětný odkaz, přes který avatar otevře zdrojovou fotku. Měnit ji smí admin, u dětí každý vedoucí, u dospělých jen napojený uživatel (`MemberProfilePhotoUpdatePermission`).
- **Heartbeat**: každý worker zapisuje každých 10 s do Redisu klíč `worker-heartbeat:<jméno>` (JSON, TTL 30 s) — stav, běžící úlohu, přijímané úlohy, CPU a paměť z cgroup (tedy z `cpus:`/`mem_limit` v compose), vytížení CPU procesu (`cpuUsage` v jádrech, rozdíl `cpu.stat` mezi heartbeaty) a počty úloh; při ukončení ho smaže. **Jméno si worker přiděluje sám** — první volný trpaslík z `WORKER_NAMES` (`config.py`, Thorinova družina, pak další; po vyčerpání `thorin-2`…), `WORKER_NAME` je jen preferované jméno, které se při obsazení přeskočí, aby šlo škálovat přes `replicas:` — zabírá ho klíčem `worker-name:<jméno>` s vlastníkem `hostname:pid` (Lua `SET` jen když je volný nebo už jeho), obnovuje ho s každým heartbeatem a při ztrátě si vezme další volné. Restartovaný kontejner (stejný hostname, PID 1) si vezme zpátky svoje jméno i po pádu. **Docker healthcheck** workeru (`python -m worker.healthcheck`) čte mtime souboru `HEARTBEAT_FILE` (`/tmp/worker-heartbeat`), který heartbeat obnoví po každém úspěšném zápisu do Redisu — starší než `HEARTBEAT_TTL_S` = unhealthy. Aplikace má healthcheck `wget` na `GET /api/health` (`HealthService`: `SELECT 1` a Redis `PING` přes `WorkersService`, každé s 3s timeoutem; při chybě 503; `start-period` 5 min kvůli migracím a reindexu), postgres `pg_isready -h 127.0.0.1` (TCP, takže neprojde dočasný server initdb). Compose čeká na `service_healthy` postgresu a redisu (`redis-cli ping`). Lokálně za TLS proxy sandboxu se image staví z kopie Dockerfile s CA proxy (`--build-context`), Docker Hub obrazy přes `mirror.gcr.io` (jinak 429). Backend je čte přes `SCAN` (`WorkersService`), starší než 25 s hlásí jako `stale`. Stránky `/admin/workery` (karta serveru z `GET /workers/server` — `ServerStatsService` čte Node `os`, tedy `/proc`, které Docker nenamespacuje, takže i z kontejneru API ukazuje celý server; vše běží na jednom serveru — a karty workerů) a `/admin/fotky/obliceje` (stav, fronta, příští dávka, tlačítko „Spustit dávku teď“ mimo noční okno a log zpracovaných fotek z `photos.faces_*` + `photo_faces`) jsou jen pro admina.
- Lokálně: `redis-server` + `REDIS_URL=redis://127.0.0.1:6379`, worker z venv `cd worker && MODELS_DIR=… DATA_DIR=… python -m worker`.

## Obsah fotek (CLIP)

- **Administrace fotek je jedna stránka `/admin/fotky`** (`PhotosAdminComponent`, na `/admin` jediná karta Fotky) s podstránkami jako child routami v obyčejném `router-outlet`: `obliceje`, `obsah`, `prirazovani-obliceju`, `kategorie` (karty kategorií s prvními fotkami, „Přidat kategorii“ v hlavičce shellu). Na desktopu (≥ lg) svislé menu vlevo, na mobilu `ion-tab-bar` v `bo-page-footer` — obojí route-based, ne přes `?tab=`. Podstránky nemají vlastní `bo-page-header`/`bo-page-content` a **`ionViewWillEnter` v nich nefunguje** (nejsou v `ion-router-outlet`) — `PhotoCategoriesComponent` se proto znovu načítá na `NavigationEnd` své URL. Editor kategorie `/admin/fotky/kategorie/:category` je samostatná stránka; staré URL (`/admin/obliceje`, `/admin/prirazovani-obliceju`, `/admin/obsah-fotek`) přesměrovávají.

- **Zero-shot, žádné pevné kategorie**: worker (`embed-photo`) spočítá pro každou fotku jednou CLIP embeddingy (512 d, z `big` náhledu) a backend je uloží do `photo_embeddings` — **řádek na výřez** (`photo_id`, `crop`), `halfvec(512)` (chyba = řádek `crop 0` s `error` a bez `embedding`). **Výřezy** (`image_crops()` ve `worker/tasks/clip.py`): `crop 0` = celá fotka doplněná na čtverec barvou průměru CLIPu, dál překrývající se čtverce přes delší stranu (`ceil(poměr stran)`, aspoň 2; u skoro čtvercových jen střed, `CLIP_CROP_MIN_ASPECT`) — **skóre fotky = nejlepší výřez**, takže se najde i věc u okraje, kterou dřívější středový ořez 224×224 zahodil (moře na 12–25 % šířky: 0,20 → 0,24–0,27). Max přes výřezy zvedá skóre obecně o ~0,01, takže hranice kategorií nastavené před `PhotoEmbeddingsCrops` je potřeba doladit; ta migrace otisky smazala a fotky se přepočítávají. Model `clip-vit-b32-crops-v2` (obraz) / `clip-vit-b32+multilingual-v1` (text). Kategorie i hledání jsou jen text → embedding → skalární součin, takže se dají měnit bez přepočtu fotek. Obrazový model je OpenAI ViT-B/32 (`Xenova/clip-vit-base-patch32`, fp16 ONNX — výsledek shodný s fp32, kvantovaný se lišil o ~0,06 kosinu), textový `sentence-transformers/clip-ViT-B-32-multilingual-v1` (kvantovaný ONNX + mean pooling + `2_Dense` projekce v numpy), takže **dotazy jdou česky**. Běží přes `onnxruntime`, ne OpenCV `dnn`. Podobnosti vychází kolem 0,2–0,3 — rozhoduje pořadí, ne absolutní hodnota. **Paměť workeru podle `WORKER_TASKS`** (naměřeno, ustálená / špička): `detect-faces` 130/220 MB, `embed-photo` 480/710 MB, `embed-text` 290/340 MB, `detect-faces,embed-photo` 730 MB, všechny tři 850/900 MB (modely se načítají líně při první úloze). **Těžké modely (`detect-faces`, `embed-photo`) se po `MODELS_IDLE_RELEASE_S` (5 min) bez úlohy uvolní** — `release()` v modulu úlohy (`RELEASES` v `tasks/__init__.py`) pod stejným zámkem jako úlohy, pak `memory.trim()`; bez `malloc_trim(0)` by glibc uvolněnou paměť nevrátil. Naměřeno 860 → 280 MB, znovunačtení ~1–2 s. `embed-text` zůstává načtený kvůli živému hledání. Compose proto pouští dva workery: těžký `detect-faces,embed-photo` (1 GB) a lehký `embed-text,match-faces` (512 MB); s jedním workerem a `"*"` chce aspoň ~1250 MB.
- **Text se embeduje ve workeru synchronně** (`embed-text`, jediná úloha s návratovou hodnotou — `__main__` vrací výsledek handleru jako `returnvalue`): `PhotoContentService.embedText()` čeká přes `QueueEvents` (`waitUntilFinished`, 30 s) a výsledky drží v LRU. Bez workeru s `embed-text` vrací hledání 504.
- **Otisky fotek jsou pgvector `halfvec(512)`, porovnává je Postgres** (`PhotoEmbeddingsService`, aplikace žádné vektory fotek nedrží): skóre fotky = `-min(e.embedding::vector(512) <#> dotaz)` přes její výřezy, `GROUP BY photo_id` + `ORDER BY` + `LIMIT/OFFSET` (`getTopPhotos`), počty kategorií jedním dotazem s `unnest($1::vector(512)[], prahy)` (`countPhotos`; dotazy musí přijít jako `vector[]` — text přetypovaný v korelovaném poddotazu se parsoval pro každý řádek, 42 s místo 1,3 s), kategorie fotky přes `getPhotoScores`. **Přetypování na `vector` je záměr**: dotaz jako `halfvec` je 3× rychlejší (75 vs 220 ms na 96k výřezů), ale skóre se liší až o 3·10⁻⁵ a fotky na hranici kategorie přeskakují; staré výsledky (JS: float32 dotaz × půlky) dává jen `::vector`. Bez indexu, přesné porovnání; HNSW by zvážit až pro hromadné dotazy. Embedding kategorie je `vector(512)` (float32); vektory kategorií se cachují v `PhotoCategoriesService`, počty do změny kategorie nebo `embeddingsVersion`.
- Plánování jako u obličejů: scheduler `photos-embed-enqueue`/`-stop` ve stejném nočním okně (`FACES_CRON`/`FACES_STOP_CRON`), `PHOTO_CONTENT_BATCH_SIZE` (3000, ~40 ms na fotku), nahraná fotka se zařadí hned, ručně `npm run cli photos-embed -- --limit N`. Admin podstránka `/admin/fotky/obsah` (`GET /photo-content`, `POST …/batch`, `GET …/search?q=`) má stav a hledání textem.
- **Kategorie jsou dynamické a přiřazení se nikam neukládá** — `photo_categories` drží název, `prompts` (popisy), `threshold` a embedding = znormovaný průměr embeddingů popisů (`meanEmbedding()`, počítá se při uložení přes `embed-text`, bez workeru 503). Fotka do kategorie patří, když `dot ≥ threshold`; `PhotoCategoriesService` to počítá v SQL, takže změna popisu či hranice platí okamžitě bez přepočtu. Spravuje admin v editoru `/admin/fotky/kategorie/:category` (`nova` + `?prompt=` z hledání; náhled `POST /photo-categories/preview` s čárou hranice ve sdílené `bo-photo-hits-grid` — s `collapse` ukáže jen první řádek, dva řádky před hranicí a dva za ní, zbytek jako tečky; řádek = počet sloupců měřený `ResizeObserver`em); s `adjustable` posouvá hranici kolečko myši (100 px = řada) nebo tah dvěma prsty (60 px = řada) — vybírá jen hranice na 3 desetinná místa ležící mezi dvěma skóre, protože `ion-range` hodnotu zaokrouhlí zpátky; `touchmove` se poslouchá na prvcích pod prsty, protože překreslená mřížka je odpojí a událost pak nebublá, vedoucí je procházejí v galerii na `/galerie/kategorie` (`PhotoCategoriesListComponent`, karty s mozaikou až čtyř nejlepších fotek kategorie (`data-count` řídí rozložení) — klik vede na `fotky?kategorie=<id>`, tužka a akce „Nová kategorie“ do editoru s `?zpet=`, kam se editor po uložení či smazání vrátí; `/galerie/kategorie/:category` přesměrovává na `fotky?kategorie=`) a filtrují na `/galerie/fotky` a vidí čipy v `bo-photos-edit` (`GET /photos/:photoId/categories`), které vedou tamtéž.
- **Procházení fotek** (`/galerie/fotky`, `PhotosBrowseComponent`) je jedno ze tří zobrazení galerie (Alba / Kategorie / Fotky) — přepíná `bo-gallery-view-switch` (`navigateRoot` bez animace): na desktopu pilulka v hlavičce u nadpisu, pod lg taby v `bo-page-footer`. Jede přes `GET /photos/browse` (`vedouci`): `q` (CLIP text → embedding přes `embed-text`, řadí podle nejlepšího výřezu, bez workeru 504), `dateFrom`/`dateTill` (den v Europe/Prague, včetně), `categoryIds` a `memberIds` — **obojí AND** (fotka musí patřit do všech kategorií a mít obličeje všech lidí) — a `emotions` (`photo_faces.emotion`, OR mezi emocemi; s `memberIds` musí mít jednu z nich každý vybraný člověk, bez nich stačí jakýkoli obličej). Výběr lidí se do URL propíše až po zavření pickeru — modal při zavření volá `history.back()`, takže `replaceUrl` za jeho běhu by se zahodil. Bez `q` řadí od nejnovějších. `PhotosRepository.browsePhotos()` skládá surové SQL (vybere id, pak načte fotky s albem), vektory kategorií dává `PhotoCategoriesService.getCategoryQueries()`. Filtr žije v URL (`q`, `od`, `do`, `kategorie`, `lide`, `emoce`).

## Sloučení členů

- **Akce „Sloučit s…“ v detailu člena** (jen admin, `MemberMergePermission`) otevře výběr člena a pak `MemberMergeModalComponent` (`dialog-merge`): oba členové vedle sebe, klik na kartu volí, kdo zůstane, u každého lišícího se údaje se vybírá strana. `POST /members/:memberId/merge` (`{ sourceMemberId, fieldsFromSource }`, cíl je v URL) a náhled počtů `GET …/merge?sourceMemberId=`. Logika je v `MemberMergeService` (`models/members/services`): v jedné transakci přepíše **všechno, co na člena odkazuje** — `events_attendees` (na společné akci zůstane jeden řádek, vedoucí má přednost), `photo_faces.member_id`/`candidate_member_id`/`notified_member_id`, kontakty (výchozí zůstane cílovému), `members_achievements`, `membership_payments` (shodný rok drží cíl) a `users.member_id` (unikátní, takže druhý účet se odpojí) — a zdrojového člena **natvrdo** smaže; soubory (kartička, profilovka) přesune po commitu. **Nový sloupec odkazující na `members` musí přibýt i sem**, jinak ho smazání zdroje kaskádou zahodí nebo vynuluje.

## Kartička pojištěnce

- `Member.insuranceCardExpiration` (`date`, nullable) drží platnost kartičky; ukládá se běžným `PATCH /members/:memberId`, smazání kartičky ji nuluje. Stav počítá `getInsuranceCardExpirationState()` (`src/helpers/insurance-card.ts`) — `unknown` / `expired` / `expiring` (do `INSURANCE_CARD_EXPIRATION_WARNING_DAYS` = 30 dní) / `valid`. Upozorňuje se na dvou místech: pilulka v kartě `bo-card-insurance-card` (červená jen u `expired`) a položka „Platnost kartičky“ v `bo-group-missing-data`, kde platí pro každého člena s nahranou kartičkou. Po nahrání kartičky se rovnou zeptáme na datum.

## API routes & links

- **Route parameters are named after their entity, never `id`** — `:eventId`, `:memberId`, `:albumId`, … The `Public API` controllers are the exception: their `:id` params are in URLs bosan.cz already calls. Renaming a param changes the SDK signature, so regenerate it.
- **`_links` hrefs substitute `:param` from the document**, so an entity-named param does not resolve from a doc that only has `id`. Each permission maps it with `params: { eventId: "id" }` — a `keyof DOC` name, or a `(doc) => …` function — applied to the **whole** href, controller prefix included. The older `path:` option only replaces the method path and duplicates the prefix; don't use it. Params the document cannot know (`:memberId` on an event link, `:size` on a photo) stay literal by design.

## Notifications

- Push + e-mail + in-app notifications live in `models/notifications` (`NotificationsService`, `PushService`); the user-facing API is `account/notifications` (`api/notifications`), linked from the API root's `_links.getNotificationSettings`. The types (`myEvents`, `submittedEvents`, `newEvents`, `newUsers`, `myBugReports`, `myPhotos`, `newAlbums`) carry Czech title, default channel and eligible roles in `schema/notification-types.ts`; a user's settings list only the types their roles allow, and per-user overrides are a `channels` enum-array (`push`/`email`/`inApp`) in `notification_settings`, stored only once changed: `[]` disables the type, a missing row or NULL means the metadata default. Selecting `push` or `email` forces `inApp` on (inlined in the controller's update route and mirrored by the settings page, which disables the forced toggle).
- **Each type belongs to a group** (`NotificationGroups`: `events` „Akce“, `photos` „Fotky“, `admin` „Administrace“ — `myBugReports` sits in Administrace). The settings response carries `group` + `groupTitle`, sorted by group order, and the settings page draws one card per group; icons live in the frontend (`GROUP_ICONS`).
- The `inApp` channel writes rows into `notifications` (`Notification` entity, `userId` is `select: false`); `GET account/notifications/items` lists the user's last 100, `POST items/:notificationId/read` and `items/read-all` set `readAt` — list, read-all and `GET items/unread-count` hang off the API root's `_links`, single-item read off each notification's. **Push payloads must use the Angular SW shape** — `{ notification: { title, body, data: { onActionClick: { default: { operation: "navigateLastFocusedOrOpen", url } } } } }` — a flat payload is silently dropped by `ngsw-worker`.
- **Počet nepřečtených drží `NotificationsService` (`core/services`)** — signál `unreadCount` plněný z `GET items/unread-count`. Načítá se při každé emisi `api.rootLinks` (tedy i po přepnutí na záložku, `ApiService.watch`) a při příchodu push zprávy (`SwPush.messages`); bez práva z `_links` (nepřihlášený) je nula a nic se neptá. Stránka s feedem počet nepřepočítává dotazem, jen ho po označení za přečtené přepíše (`setUnreadCount()`) ze svého seznamu. Zobrazuje ho `bo-unread-badge` (skrytá při nule, nad 99 „99+") u položky Notifikace v sidebaru i v účtovém popoveru a červená tečka na avataru (`account-menu`) — bez ní by byl na mobilu počet schovaný v zavřeném menu.
- Frontend: `/ucet/notifikace` is the feed (unread dot, click marks read and navigates the notification's `path`, mark-all + settings in header actions; item also in the sidebar and avatar popover), `/ucet/notifikace/nastaveni` the settings (channel toggles per type, device list with test/delete, "Zapnout na tomto zařízení"). `PushNotificationsService` (`core/services`, activated in `AppComponent`) owns the `localStorage.notificationsDeviceId`, subscribes via `SwPush` and on app start re-POSTs the current subscription **only if the device is still in the backend list** — re-adding one deleted elsewhere would resurrect it. `SwPush` is disabled in dev builds, so the subscribe UI degrades to "prohlížeč nepodporuje" there.
- **VAPID keys arrive at runtime** via `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` (generate with `npx web-push generate-vapid-keys`; `VAPID_SUBJECT` optional). Unset keys disable push cleanly — `pushEnabled: false`, no public key served, sends skipped — while e-mail keeps working.
- A device is a row in `notification_subscriptions`, unique per `(userId, deviceId)` where `deviceId` is a client-generated id kept in the browser. `POST account/notifications/devices` upserts by that pair, so a rotated endpoint/keys update the same row instead of duplicating the device; any other row holding the same endpoint (globally unique) is deleted first. The endpoint is a capability URL and the keys decrypt only that device's payloads, so all three are `select: false` and never leave the backend. A push send answered 404/410 deletes the subscription — that applies to `POST devices/:deviceId/test` too, which otherwise verifies the whole chain.
- Notification triggers are fire-and-forget calls from controllers (`.catch` + log, never blocking the response): event submit → `submittedEvents` to program+admin; publish → `myEvents` to the event's leaders and `newEvents` to everyone else; reject/cancel/uncancel → `myEvents` to leaders; user create → `newUsers` to admins; album publish → `newAlbums` (inApp default) to every user with an active member or admin. **The acting user is excluded**, so publishing your own event notifies you of nothing — `NOTIFY_ACTOR=true` keeps them in and makes the whole chain testable on one account (logs a warning at start; test environments only).
- **E-mail and push go through the BullMQ queue `notifications`** (registered in `NotificationsModelModule`, enqueued by `NotificationsQueueService`; the processor sits in `NotificationsProcessorModule`, imported by `app.module` only; delivery itself in `NotificationsDeliveryService`): one job per e-mail / per push subscription, 6 attempts with exponential backoff from 30 s, concurrency 5, processed only by the API process (the CLI just enqueues). A push job carries only `subscriptionId` — endpoint and keys are re-read from the DB, never stored in Redis; a 404/410 deletes the subscription instead of retrying. Other 4xx (except 401/403/408/429 — auth, Gmail rate limits, timeouts) end the job at once via `UnrecoverableError`; status is read from `statusCode` (web-push) or `status`/`response.status` (gaxios). In-app rows are written synchronously; the login link, bug report e-mail and `devices/:deviceId/test` stay synchronous.
- **`myBugReports` notifies the reporter once the fix is in production**, and is the one trigger that fires from `main.ts` rather than a controller: the deploy job only pings Watchtower, so CI never learns when the new backend is actually up, and a plain restart or a rollback would bypass it entirely. After `app.listen()` (fire-and-forget) `ReleaseNotificationsService` reads `release-issues.json` and notifies the reporters of the issues in it. It skips silently when the file is missing (dev), when its version is not a `v*` release (NEXT builds) and — with a warning — when the version does not match `config.app.version`. `POST /feedback/bug` records a `bug_reports` row (`userId`, `repo`, `issueNumber`, `title`, unique per repo+issue, insert `orIgnore`) plus `path` — pathname/search/hash of the page the report was sent from, which the notification links to (fallback `/ucet/chyby`) — and whose **`notifiedAt` is the only idempotence state** — no bookkeeping of released versions, so restarts and rollbacks re-send nothing. The row is written only when a GitHub issue was actually created, and a failed write is logged rather than failing the report.
- **`myPhotos` je denní souhrn nově rozpoznaných fotek** (jen `inApp`, role `vedouci`) — rozpoznávání obličejů je asynchronní, takže jde z BullMQ scheduleru `faces-notify` (`FACES_NOTIFY_CRON`, 7:00 Europe/Prague, po nočním `faces-match`; ručně `npm run cli faces-notify`). `PhotoFacesNotificationsService` vezme obličeje, kde `member_id` ≠ `photo_faces.notified_member_id` — počítá se každá fotka, i stará nově přiřazená — pošle za člena jednu notifikaci napříč alby a obličejům zapíše člena a čas běhu (`notified_at`); znovu se ohlásí jen obličej přeřazený jinému členovi. Migrace označila všechna dosavadní přiřazení za ohlášená. Odkaz vede na samostatnou stránku `/galerie/nove-fotky/:member/:notifiedAt` (`MemberNewPhotosComponent`, ms běhu) s fotkami z té notifikace seskupenými po albech (`GET /members/:memberId/photos?notifiedAt=`, přesná shoda s `notified_at`; odpověď nese i `album`); „Všechny fotky“ vede na záložku Fotky v profilu člena. Příjemce je uživatel napojený na aktivního člena (nebo admin); obličej, který si uživatel ručně označil sám, se tiše odbaví bez `notified_at` (`NOTIFY_ACTOR` ho pustí).
- **`GET /feedback/bugs` lists the caller's own reports** — the page `/ucet/chyby`, opened from the "Moje nahlášené chyby" button in the report dialog and the target of the `myBugReports` notification. The state is derived, never stored, and **never asks GitHub** — one issue lookup per report made the page load visibly late: `release-issues.json` (or `notifiedAt`) → `released`, the row's only badge ("Opraveno", with the release version in its meta line); `open` deliberately shows none. Closing an issue therefore shows nothing until the fix ships. The row is not a link — a GitHub icon at its right opens the issue, so the rest of the line stays free. The report dialog had to become a component (`BugReportModalComponent`) to carry the second button, now a clock icon at the right of its title line — the footer keeps the two confirming buttons alone, or the three of them do not fit one line on a phone (#478); the sidebar and the account menu both open it through `BugReportService`.
- **Hlášení chyby s sebou nese i diagnostiku prostředí** — jde jen do issue a do e-mailu, nikam se neukládá. `BugReportService` posílá verzi frontendu (`Config.version`), rozlišení obrazovky (`screen.width`/`height` v CSS px) a `devicePixelRatio`, velikost okna (`innerWidth`/`innerHeight`), režim zobrazení (`display-mode` + `navigator.standalone` → `browser`/`standalone`/`minimalUi`/`fullscreen`, enum `BugReportDisplayModes` — pozná instalovanou PWA) a typ ovládání (`any-pointer: fine`/`coarse` → `fine`/`coarse`/`both`/`none`, enum `BugReportPointerTypes`); **fyzické rozlišení dopočítává backend** z CSS px a ratia, a protože ty prohlížeč zaokrouhluje, je výsledek na pixel nepřesný a nese `≈`; backend přidá svou verzi (`config.app.version`) a z **hlavičky `User-Agent`** (tu frontend neposílá) vytáhne systém a prohlížeč — `parseUserAgent()` v `helpers/user-agent.ts`, prosté regulární výrazy bez závislosti. Do issue jde i celý User-Agent, protože parser umí vedle sáhnout; Windows 10 od 11 ani verzi macOS pod Safari (to hlásí napořád 10.15) z UA poznat nejde.
- **`ReleaseIssuesService` (`models/bug-reports`) owns `release-issues.json`** for both readers — the bug list and `ReleaseNotificationsService`. It caches the parsed file for the life of the process, which is exactly its lifetime: the file is baked into the image and only a deploy changes it.
- **An issue only reaches `release-issues.json` if the fixing commit references it** (`Closes #123`, or `(#123)` in the subject) — the same rule as the changelog, and forgetting it silently costs the reporter both their notification and the "Opraveno" badge.

## Offline režim

- **Databáze offline je vlastní úložiště v IndexedDB, ne cache service workeru** (`core/offline`). Stahuje se **sama každému s `_links.listMembers`** (`OfflineDataService.sync()`, bez zapínání; `bo-account-offline` v Nastavení jen ukazuje stav a „Aktualizovat“): kořen API, účet, oddíly, **jen aktivní** členové (s kontakty), detail a kontakty každého z nich a kartičky pojištěnce (generace záznamů, 4 souběžně). **Kartička se znovu nestahuje** — `GET …/insurance-card` posílá `ETag` (velikost + mtime souboru) a na `If-None-Match` vrací 304; ETag je v záznamu `insurance-card-etag:<id>` a při 304 se do nové generace přepíše uložený blob. Stav (`userId`, `downloadedAt`, počty) je v `localStorage.offlineData`; po 12 h online se stáhne znovu potichu, **změna nebo odhlášení uživatele data smaže**.
- **Čte se v interceptoru vlastní axios instance `ApiService`**: GET, který spadne na síti (nebo dostane od SW prázdné 504), se zkusí obsloužit `resolveOfflineResponse()` — seznamy členů a oddílů filtruje, řadí a stránkuje na klientovi podobně jako backend (hledání je podřetězec bez diakritiky, ne fulltext). Stahování samo jde s `offlineFallback: false`. `ApiService.offline` (signál) řídí úvodní stránku — offline jen varování a dlaždice toho, co funguje (Databáze). Úpravy offline nejsou. `dataGroups` v `ngsw-config.json` jsou proto pryč; SW drží jen aplikaci.

## Backend entities

- **One table, one entity mapping.** Never map a table twice (an explicit `@Entity("x")` _and_ a `@JoinTable` over `"x"`): TypeORM builds two metadata objects and **every** generated migration then drops and recreates that table's indexes — drift that survives being applied. `events_groups` is mapped **only** by the `@ManyToMany`/`@JoinTable` on `Event.groups` and must never get an entity again; code touching it directly works off the table name (`clearJoinTable()` in `mongo-import.service.ts`).
- **`Event.groupsIds` is a `@RelationId`, so it is read-only.** Writes go through the relation: `EventsRepository.updateEvent()` turns `groupsIds` into `groups` references and lets the cascading `save()` sync the join rows.
- **Files imported from the old server keep their Mongo ObjectId** in `Event.srcId` / `Photo.srcId`+`srcAlbumId` and stay in the legacy on-disk layout (folder keyed by the ObjectId, `registration.pdf`); native records use the numeric-id layout (`prihlaska_<name>.pdf`). Resolution coalesces on `srcId` — see `PhotosFilesService.getPhotoImagePath` and `EventsRegistrationsController`.

## Database migrations

- **Always** generate migrations with `npm run migrations:generate --name=<Name>` from `backend/` — never by hand, never `migrations:create`. Change the `@Column`/`@Entity` definition first (collation, type, nullable, indexes) and let the generator diff it against the DB.
- **Always read and fix up the generated migration before running it**: delete unrelated drift the diff swept in (it compares _all_ entities); add by hand what TypeORM cannot generate (`CREATE COLLATION`, extensions, text-search configs) ahead of the statement needing it — see `*-GroupNameNaturalNumericCollation.ts`; and make sure `down()` really reverses `up()`.
- **Generated columns must be registered in `typeorm_metadata`**, or every later generate drops and recreates them: pair each `ADD` with the `INSERT INTO "typeorm_metadata"` the generator emits and each `DROP` with a `DELETE`, but use `current_database()` instead of a hardcoded DB name. `*-SearchVectorColumns.ts` is the reference: it also creates the `unaccent` extension and `simple_unaccent` config, and — since TypeORM cannot express `USING gin (...)` — declares the GIN index with `@Index("…", { synchronize: false })` and creates/drops it by hand.
- **Full-text search uses stored `search_vector` tsvector columns** on members, members_contacts, events, albums and users, built with `to_tsvector('simple_unaccent', …)` (the 2-arg form is IMMUTABLE, so it is legal in a STORED column). `simple_unaccent` is `simple` with word tokens remapped through `unaccent` → case- and diacritic-insensitive. Query with `search_vector @@ to_tsquery('simple_unaccent', :q)` and build `:q` via `toPrefixTsQuery()` (`helpers/search.ts`). It matches whole words and prefixes only — not mid-word substrings (that would need `pg_trgm`).
- **Members and their contacts are also searched by phone and e-mail** (#362). The column expression normalises phones (separators between digits dropped, so `777 123 456` is one token; leading `+420`/`00420` stripped, a bare `420` kept — `4xx xxx xxx` is a real landline range) and splits e-mails with `translate(…, '@._+-', '     ')`, or the parser emits the whole address as a single token. `toPrefixTsQuery()` normalises phones the same way — **change one and you must change the other**. A generated column only sees its own row, so `MembersRepository.getMembers()` ORs the member's vector with an `EXISTS` over their contacts' vectors.
- Apply and verify rather than assume: `migrations:run`, check the schema/data, `migrations:revert` to test both directions, then `migrations:generate` once more — a clean change reports _"No changes in database schema were found"_. Migrations auto-run in production only; in dev, apply them yourself.

- **pgvector** (`vector`, `halfvec`; otisky fotek, obličejů a kategorií): TypeORM 0.3.28 ty typy zná (`type: "halfvec", length: 512`, pole čísel se převádí samo), takže se generují i diffují normálně; `CREATE EXTENSION "vector"` je ručně na začátku `PgvectorEmbeddings` a TypeORM ho navíc zkouší vytvořit při každém připojení. `halfvec` potřebuje pgvector ≥ 0.7 a `CREATE EXTENSION IF NOT EXISTS` starou verzi nepovýší (`ALTER EXTENSION vector UPDATE`). Produkce i devcontainer běží na target `postgres` z kořenového `Dockerfile` (`postgres:15-bookworm` + `postgresql-15-postgis-3` + `postgresql-15-pgvector` z PGDG, image `bosancz/interni-sekce-postgres`; dřív `postgis/postgis:15-3.5` na bullseye). **Změna systému pod databází mění verze kolací** (glibc 2.31 → 2.36, ICU `natural_numeric` 153.14 → 153.120) a textové indexy pak mohou řadit špatně, takže produkční start před migracemi volá `refreshDatabaseVersions()` (`database/refresh-database-versions.ts`, ručně `npm run cli db-refresh-versions`): při nesouladu verze kolace databáze nebo vlastní kolace `REINDEX DATABASE` + `REFRESH COLLATION VERSION` a každé rozšíření s novější nainstalovanou verzí `ALTER EXTENSION … UPDATE` (PostGIS 3.5 → 3.6); jinak nic nedělá. Selhání jen zaloguje. Připojuje se jako `postgres` (superuser).

### Running Postgres and Redis in a cloud/sandbox session

Postgres 16 is preinstalled but **cannot run as root** — use the unprivileged `postgres` user.

```bash
PGBIN=/usr/lib/postgresql/16/bin
PGDATA=/tmp/pgdata; rm -rf "$PGDATA"; mkdir -p "$PGDATA"; chown postgres:postgres "$PGDATA" /tmp
su postgres -c "$PGBIN/initdb -D $PGDATA -U postgres --auth=trust"
su postgres -c "$PGBIN/pg_ctl -D $PGDATA -o '-p 5432 -k /tmp -c listen_addresses=127.0.0.1' -l /tmp/pg.log start"
PGPASSWORD=postgres psql -h 127.0.0.1 -U postgres -c "CREATE DATABASE interni;"
PGPASSWORD=postgres psql -h 127.0.0.1 -U postgres -c "ALTER DATABASE interni SET app.environment = 'test';"
PGPASSWORD=postgres psql -h 127.0.0.1 -U postgres -d interni -c "CREATE EXTENSION IF NOT EXISTS postgis;"
redis-server --daemonize yes --port 6379
export DB_HOST=127.0.0.1 DB_PORT=5432 DB_USER=postgres DB_PASSWORD=postgres DB_DATABASE_NAME=interni DB_SCHEMA=public REDIS_URL=redis://127.0.0.1:6379
cd backend && npm ci && npm run migrations:run
```

**pgvector ≥ 0.7** is needed too, and Ubuntu's `postgresql-16-pgvector` is 0.6 (no `halfvec`) while PGDG's package wants a newer `postgresql-16`. Add the PGDG repo (`https://apt.postgresql.org/pub/repos/apt noble-pgdg main`, key `ACCC4CF8.asc`), `apt-get download postgresql-16-pgvector`, `dpkg -x` it and copy `vector.so` into `/usr/lib/postgresql/16/lib` and `vector*` into `/usr/share/postgresql/16/extension` (before the first `migrations:run`, or `DROP EXTENSION vector` afterwards).

**PostGIS** (needed by `Event.placeGeometry`) is not preinstalled: if `CREATE EXTENSION postgis` fails, `apt-get update && apt-get install -y postgresql-16-postgis-3` — the `update` is required. `unaccent` ships with core.
