# Project notes

## Code style

- **No explanatory comments anywhere** — TS, templates, SCSS, migrations. What is worth remembering across sessions goes into this file; a note to the reviewer goes into the commit message. `TODO`/`FIXME` and tool directives (`@ts-ignore`, eslint) are fine. Keep this file compact.
- **Injected dependencies:** services carry the `Service` suffix (`private notificationsService: NotificationsService`), repositories the full entity name without it (`private notificationSettings: NotificationSettingsRepository`).
- **Prettier formats the repo**: `./backend/node_modules/.bin/prettier --write .` from the root (`.prettierrc.yml`: tabs, width 120). `.prettierignore` holds `!old`, `frontend/src/sdk`, `frontend/src/assets/lib`, `backend/assets` and `CHANGELOG.md` out of it.
- `!old/` is the retired server kept for reference — never edit it.

## Commits & changelog

- **Conventional Commits** (`type(scope): description`), enforced by commitlint. **Description in Czech**, `type`/`scope` in English: the visitor-facing changelog takes subjects **verbatim**.
- **An issue reaches the changelog only if the commit itself references it** — `Closes #123` (also `Fixes`/`Resolves`/`Refs`) in the commit body, or `(#123)` in the subject. PR bodies are not git history; merges are skipped (`--no-merges`).
- `scripts/generate-changelog.mjs` **prepends** the new version's section to `CHANGELOG.md`, so older sections survive edits. One flat list per version, each entry led by its type's gitmoji (`feat` ✨, `fix` 🐛, `style` 🎨, `perf` ⚡️, `refactor` ♻️, `docs` 📝, `test` ✅, `build` 📦️, `ci` 👷, `revert` ⏪️, `chore` 🔧, and last ❓ for non-conventional subjects, taken whole). A non-conventional subject repeating a typed commit's description merges into that entry. Served at `GET /api/changelog`; the version in the menu opens it.
- Each entry links to its commit and ends with its authors' **avatars**: author linked to GitHub, committer (usually Claude) tucked 60 % behind — no link, one shared tooltip ("Kopec a Claude"); commits committed by GitHub's own web UI show the author alone. Accounts resolve from GitHub no-reply emails, else `GET /repos/:o/:r/commits/:sha` (needs `GITHUB_TOKEN` and the commit pushed); no account → initials circle, a failed lookup costs only the avatar. `--no-authors` skips the API. Markup hangs off `changelog-credit`/`-author`/`-committer`/`-avatar` in `changelog-modal.component.scss`; `ChangelogLinksPipe` links `#123` and opens everything in a new tab. Pre-2023 sections came from the legacy `bosancz/bosan.cz` repo — commit links, no `#nnn`.
- Released sections are never regenerated, so changed markup needs `--backfill` (re-renders only each entry's gitmoji and credit, idempotent, matches by commit link so the hand-written `v4.0.0` entry stays untouched). `--backfill-other` appends the ❓ entries missing from each tag range (needs `git fetch --unshallow --tags`, idempotent, skips hand-written sections).
- **Both releases generate the changelog in the build job.** `build.yml` runs the generator before `docker build` whenever `changelog-version` is set; `changelog-branch` decides whether the file is kept. PRODUCTION passes `vN.N.N` + `changelog-branch: master` → committed and pushed **after** the image is published (a failed build must not record a version that never shipped), and `tag.yml` tags that commit. NEXT passes `NEXT-<short sha>` and no branch → the section lives only inside the image. The range is always "since the last `v*` tag".
- **The generator also writes `release-issues.json`** next to `CHANGELOG.md` — `{ version, date, repo, issues: [{ number, version, text }] }`, **cumulative**: every issue any section has ever recorded, re-read out of the rendered markdown after the prepend, so a release the running container never booted (two releases in quick succession) still notifies its reporters. Per issue it keeps the **earliest** version that carried it, sections being newest-first. Gitignored and never committed — `build.yml` stages only `CHANGELOG.md` — it reaches the image through the Dockerfile's `COPY release-issues.jso[n]`, the glob keeping a build without the generator working.

## Dev workflow

- **Never start a second dev server, or run `ng build`/`npm run build`, while one is already running.** Root `npm run dev` runs frontend + backend via `concurrently` and tees to `dev.log` (gitignored, `[FE]`/`[BE]` prefixes, raw ANSI). Verify your change by reading it (`tail -n 80 dev.log`); an error there may be another agent's in-flight change.
- **A missing or stale `dev.log` means no server is running** — you are in a fresh sandbox and are expected to start one, not to ship unverified.
  - **Angular needs Node 24**; the sandbox default (22.x) fails every `ng` command on the engines check. `nvm install 24` (`NVM_DIR=/opt/nvm`).
  - `npm ci` works in `frontend/` and `backend/`. Do **not** run the root `npm ci` — `scripts/install.sh` also builds the backend and runs migrations, so it needs a database. Don't commit lockfile churn from `npm install`.
  - Frontend-only change: `cd frontend && npm ci && npm run dev`. Backend change or the full root `npm run dev`: bring up Postgres first (below).
- **`.mcp.json` registers the Angular CLI MCP server** (`npx -y @angular/cli mcp`) — docs/best-practices plus workspace tools, run from the repo root, Node 24 like every `ng` command; its `devserver_start` falls under the one-server rule.

Data jsou v `seed/data/seed-data.ts`. Akce se počítají od nejbližší soboty podle `schedule` (víkend so–ne, prodloužený víkend pá–ne, týden so–so) a `weeks`, takže padnou vždy na správné dny v týdnu a do budoucna; akce bez vedoucích může být jen `draft`, protože ji nemá kdo podat ke schválení — hlídá to `assertSeedEventStatuses()` a seed na nekonzistentních datech spadne dřív, než začne zapisovat. Seed proto u svých akcí nuluje i `statusNote` a značky odeslané ohlášky a vyúčtování, aby po změně statusu v datech nezůstaly viset z předchozího běhu. Fotky alba jsou soubory v `backend/assets/seed/photos` (assety se kopírují do image, cesta je relativní ke cwd jako u ostatních assetů) a seed je ukládá přes `PhotosFilesService.savePhotoFiles()`, takže vzniknou i náhledy v `DATA_DIR`.
- Příkaz je **idempotentní** — záznamy hledá podle přirozeného klíče (login / přezdívka / název) a aktualizuje je; kontakty, účastníky a útraty seedovaných záznamů přepisuje. Nic jiného v databázi nemaže, takže se dá pouštět i na prostředí s importovanými daty.
- **Kam se smí seedovat, rozhoduje značka v databázi** — `ALTER DATABASE <db> SET app.environment = 'test'` (resp. `'production'`). Bez značky příkaz odmítne běžet (i ve vývoji) a vypíše hotové SQL i to, že jde použít `--force`; databáze označená jako produkční se odmítne vždy, ani `--force` nepomůže. Značku nepřenáší `pg_dump` (jen `pg_dumpall`), takže obnova dat z produkčního dumpu do testovací databáze o ni nepřijde a špatně nasměrovaný `DB_HOST` seed zastaví.
- `npm run cli reset-db` zahodí schéma (`DROP SCHEMA ... CASCADE`) a spustí všechny migrace od začátku, s `--seed` rovnou naplní i testovací data; řídí se stejnou značkou. Rozšíření (`postgis`, `cube`, `unaccent`), kolaci i konfiguraci fulltextu vytvářejí samy migrace, značka `app.environment` visí na databázi, ne na schématu — po resetu tedy nic nechybí. Se schématem ale padnou i rozšíření v něm a `CREATE EXTENSION postgis` smí jen superuser (`cube`/`unaccent` jsou trusted), takže příkaz předem odmítne drop na nesuperuserovém spojení, aby databázi nenechal rozbitou uprostřed migrací. V kontejneru je to jediná cesta: `npm run migrations:*` jedou přes `ts-node`, který je devDependency a v image chybí.
- `SEED_ON_START=true` naplní data při každém startu aplikace (po migracích, `main.ts`) — tahle cesta `--force` nezná, bez značky `test` nebo bez `SEED_PASSWORD` se jen přeskočí s chybou v logu.

## Frontend SDK

- `frontend/src/sdk` is generated from the backend's OpenAPI spec — never hand-edit `api.ts`. After changing a backend controller/DTO run `npm run generate:sdk` from `frontend/` (reads `http://127.0.0.1:3000/api/openapi-json`, so the backend must be up). Every NestJS route needs a unique `operationId` (method name) or generation fails validation.

## User settings

- **`User.settings` is an opaque `jsonb` blob owned by the frontend** — the backend never looks inside it. `GET /account/settings` and `PUT /account/settings` (whole object, `{ settings: … }`, `@IsObject()` only) are the only way in; the column is `select: false`, so it never rides along in `getMe` or the users list. Unknown keys survive a round trip untouched.
- Frontend goes through `UserSettingsService` (`core/services`): `watch(key)` returns a signal, `set(key, value)` writes through to `localStorage.userSettings` (instant, survives the reload before the API answers) and PUTs the whole object; requests are queued so they cannot overtake each other.
- **Only the keys in `PROPAGATED_SETTINGS` follow a change made in another tab** — just `darkMode`. Everything else is a per-tab working state that is still _saved_ for the next load: two tabs may show different columns or a different album view at once. The service keeps `stored` (what is persisted) apart from `pinned` (what this tab insists on showing), the view being `{ ...stored, ...pinned }`; an external change pins whatever the tab currently shows for the non-propagating keys before adopting the new `stored`. It pins the keys the tab has **watched**, not the keys already present — pinning only what `stored` happened to contain let the very first write of a key through to every other tab; pinning `undefined` for a watched-but-unset key keeps that tab on its defaults, while a tab that never watched the key adopts the new value when it later opens that page. The receiving tab never PUTs the echo back, and writes build on `stored`, so a tab holding an old view cannot push it back over another tab's. Whole keys are last-write-wins, so the last tab to touch `membersListColumns` defines the saved default.
- **`LocalStorageService.watchExternal()` sees only other tabs' writes**; `watch()` also fires for this tab's own `set()` and emits the current value on subscribe. Its `storage` handler parses `newValue` — it used to hand subscribers the raw JSON string on the cross-tab path and the parsed value on the same-tab one, so a cross-tab `false` arrived as truthy `"false"`. On login it loads from the server, but an **empty** server object with a non-empty local one is pushed up instead — that migrates the pre-existing `isDarkMode` / `albumsListView` keys, which `readCache()` still reads on first run.
- Persisted so far: `darkMode` (`DarkModeService`, injected in `AppComponent` so the theme applies before the sidebar exists), `albumsListView` and `membersListColumns`.
- **The members list merges its saved columns over `MEMBERS_LIST_COLUMNS`**, so a new column takes its default and a removed one drops out. The write goes to the settings only; an `effect` on the watched signal applies it, which is also what picks up the server's copy arriving after the first paint (and reloads the list when a contact column appears). That effect reads `viewSelections` for the previous state and writes it, so the read is wrapped in `untracked()` — without it the effect retriggers itself and hangs the page.

## Public API (bosan.cz)

- The iCalendar feed is `GET /api/public/program/ical` (`ProgramIcalService`, `ical-generator`). `ProgramIcalLegacyController` keeps the old server's `/api/program/ical` alive — deprecated in OpenAPI, same body. Never drop it without warning: ICS subscriptions are set-and-forget.
- Events are **all-day**: `DTEND` is exclusive (`dateTill + 1 day`) and the calendar deliberately sets **no** timezone (with one, `ical-generator` renders `DTSTAMP` as floating local time, which is invalid; the Luxon values carry `Europe/Prague` themselves). `timeFrom`/`timeTill` are free text ("ráno") and are never parsed.
- Cancelled events stay in the feed as `STATUS:CANCELLED` with a `Zrušeno: ` summary prefix. `UID` is `event-<id>@bosan.cz`, stable so clients update instead of duplicating. Window: `ICAL_DAYS_BACK` (30) back, unbounded forward; `EventsRepository.getPublicProgramIcal()` skips the 100-row cap of the JSON program endpoint.
- bosan.cz resolves the feed URL from the API root's `_links` (`program:ical`), falling back to a hardcoded URL — the hardcoded one going stale is what broke this originally (#352).

## Event statuses

- **`EventStates` (`event.entity.ts`) is `draft`, `pending`, `rejected`, `public`, `cancelled`.** `rejected` was dropped from the DB enum in 2023 (`1682264978418`) and reintroduced by `EventStatusRejected1787131906960`, so **"Vrátit k úpravám" (`POST /events/:eventId/reject`) sets `rejected`, not `draft`** — a returned event is distinguishable from one never submitted. That migration's `down()` maps `rejected` back to `draft` before narrowing the enum, or the cast fails.
- A `rejected` event is back in the leader's hands: `EventSubmitPermission` and `EventPublishPermission` treat it like `draft` (`events.acl.ts`). `POST /events/:eventId/unpublish` still returns to `draft` — removing from the programme is not a rejection. Nothing else branches on it; the public programme and iCal feed only match `public`/`cancelled`. `EventStatuses` (frontend `core/config/event-statuses.ts`) also carries `finalized`, which no backend code sets, so code mapping over statuses must tolerate it; `GET /events/statuses` returns the statuses actually present, so the list filter picks up new ones itself.
- **The announcement and the accounting are handed in outside the system**, so `Event.announcementSentAt`/`accountingSentAt` only record that someone marked them sent — `POST/DELETE /events/:eventId/announcement/sent` and `/accounting/sent`, applicable only on a `public` event, the DELETE undoing a mistaken click; permissions inherit `EventEditPermission`.
- `bo-event-progress` (event view, between header and content) always shows five points: příprava / schvalování / program, "Ohláška" ("Ohláška odeslána" once marked) and "Uzavřená n/3" — filled up to the active one, grey until reached. **Each step carries its own accent**: `--accent` for its dot and the rail leading into it, `--accent-out` (the next step's accent) for the trailing segment, so the whole line between two dots takes the colour of the dot it leads into. Points 1–3 take the status accent — `EventStatuses[status].color`, except `draft`, which is grey (`EventStatuses.draft.color`) without leaders and orange with them, a leaderless draft having nothing in progress yet. **`rejected` sits in point 1**, not 2 — it is back in the leader's hands — and labels it "Vrácená k úpravám"; point 2 reads "Schválena" once past it (`PAST_STEP_LABELS`). A `statusNote` adds a chat icon opening an `ion-popover` — popover content renders outside view encapsulation, so its styles are `::ng-deep`, as in `home-card-top-leaders`.
- **Point 5 counts all three closure items but only two of them gate it** — vyúčtování and report carry `EventClosureItem.required`; the gallery counts into `n/3` yet never blocks, so "Uzavřená 2/3" is a legitimately finished event. **Point 5 only lights up once there is something to close**: after the announcement is marked it stays grey while the event is still running (`dateTill` not yet past) and nothing required is done, so the highlight rests on point 4; from the day after `dateTill` it goes orange (`EventStatuses.pending.color`), and both required items done turn it green (`EventStatuses.public.color`) whenever that happens, even before the event ends.
- The whole step block is the click target (tinted hover on the label text) and opens a centred dialog via `ModalService.componentModal` like every other modal: `EventAnnouncementModalComponent` and `EventClosureModalComponent`, checkbox forms extending `InputModalComponent`. Closure lists accounting (the one tickable checkbox), report (derived from `event.report`) and gallery (from `event.album`: missing / `draft` / `public` — `getEvent()` joins it), the derived two disabled and the gallery marked "Nepovinné". The component calls the API on the modal result and emits `(change)` so `event-view` reloads.
- **The ŠÁN dialog chrome lives in `bo-modal-layout`, so every modal inherits it** — heading in the body font (the display font is reserved for headlines) with a yellow accent bar (`::after` on `.title`, keeping the `.title:empty` rule working for title-less sheets), brand paddings and footer border. Projected headings carry the caller's scope, so they are restyled via `::ng-deep` and inherit their size from `.title` — the changelog's `h1 { font-size: inherit }` depends on that. The card (radius, shadow, blue-tinted backdrop) is on `ion-modal.dialog`; `dialog-brand` only pins the width of the two event dialogs. Their row/button styles are in `src/styles/_brand-modal.scss`, tokens on `:host` plus a `:host-context(body.dark)` block so the handoff's light values don't break dark mode.
- **Bootstrap is loaded globally, so `.modal-header`/`.modal-body`/`.modal-footer` are taken** — its rules centred the title. Component classes there are prefixed `bm-`.
- **Správce programu (`program`) vede akci po obsahové stránce, ne po účastnické.** `EventEditPermission` mu dává `program: true`, takže edituje název, popis, sraz, oddíly, přihlášku i report. Vedoucí přidává přes vlastní routu `PUT /events/:eventId/leaders/:memberId` (`addEventLeader`, upsert — z účastníka udělá vedoucího) s `EventLeaderCreatePermission`, která dědí `EventEditPermission`; funguje i na akci bez vedoucích, takže si ji nemusí nejdřív vzít (`leadEvent` zůstává pro vedoucí). Odebírá se pořád přes `DELETE …/attendees/:memberId` — `EventAttendeeEditPermission` (a z ní děděná delete) k tomu pouští `program` jen u řádku s `type === "leader"`, takže účastníky ani výdaje nepřidá ani neodebere. Ve frontendu tlačítka rozlišuje `canAddLeader()` / `canAddAttendee()` (`event-attendees`); dva linky = dvě routy, jedna routa nese v `_links` jen jeden.
- **Report patří vedoucím akce, ne správci programu.** `EventReportEditPermission` má vlastní `vedouci: isMyEvent` (nedědí `EventEditPermission`) a visí na `PUT /events/:eventId/report` — jediné cestě, jak report uložit: `EventUpdateBody` pole `report` **nemá**, takže `PATCH /events/:eventId` s ním skončí na 400. Fotogalerie zůstává na `updateEvent` a připojuje se přes `PATCH /albums/:albumId`, tam se práva zatím neřešila.
- **Tlačítko bez práv se nezhasíná, ale zakazuje** — `[disabled]` + `[boTooltip]="…nemáš oprávnění."` (text `noPermissionText`, jako v `bo-action-buttons`). `ion-button.bo-tooltip.button-disabled` v `styles/ionic.scss` mu vrací `pointer-events`, takže tooltip najede i na zakázaném tlačítku.
- **Karta akce (`event-card`) je v záložce Info vidět v každé šířce** — `order-first order-xl-last`, na mobilu tedy nad seznamem údajů. Je to jediné místo, kde je bez rozkliknutí vidět „Vede …“ (#415).
- **A modal's "can I edit this" flag must read the persisted value, not its own checkbox signal** — `unmarkX.allowed` is false while `xSentAt` is null, so deriving it from the checkbox disables the save button the instant the box is ticked.

## People picker

- **`MemberSelectorModalComponent` is the only picker on people.** It wraps `bo-modal-layout` like every other modal — title/subtitle + ✕ in the title slot, sticky search and group chips above the scrolling list, count and buttons in the footer (design handoff "Výběr lidí", #357). `dialog-picker` pins it to 560 px / 720 px.
- Ionic assigns `componentProps` as plain properties, so `selectedIds` is a **`Signal<number[]>` owned by the caller** — that is what repaints the checked state when the underlying list changes. Without it the picker is single-select: no checkboxes, no count, "Zrušit", closes on the first pick (`users-view`).
- With `keepOpenAfterSelect` the modal stays open, the button reads "Hotovo" (everything is already saved) and `onSelect`/`onDeselect`/`onClearAll` may be async — the row shows a spinner and ignores further clicks meanwhile. `event-attendees` adds, removes and (confirmed) clears through it; unchecking a single leader there is deliberately not confirmed, unlike the list's delete button, because one more click puts them back.
- **Filtering never touches the selection** — the footer count is the source of truth. Search is diacritics-insensitive substring over nickname + first/last name; group chips come from the groups actually present in the loaded list. Group tags tint the group's own colour (`rgba` + a fixed-lightness `hsl`, both themes as `--mp-tag-*` custom properties) instead of the solid badge used in lists.
- **Content projection ignores `slot=` on elements inside `@if`** — the footer must be projected unconditionally, with the branch inside it, or it silently lands in the default slot. The host also needs `display: flex; max-height: 100%`, or the list overflows past the footer instead of scrolling.

## API routes & links

- **Route parameters are named after their entity, never `id`** — `:eventId`, `:memberId`, `:albumId`, … The `Public API` controllers are the exception: their `:id` params are in URLs bosan.cz already calls. Renaming a param changes the SDK signature, so regenerate it.
- **`_links` hrefs substitute `:param` from the document**, so an entity-named param does not resolve from a doc that only has `id`. Each permission maps it with `params: { eventId: "id" }` — a `keyof DOC` name, or a `(doc) => …` function — applied to the **whole** href, controller prefix included. The older `path:` option only replaces the method path and duplicates the prefix; don't use it. Params the document cannot know (`:memberId` on an event link, `:size` on a photo) stay literal by design.

## Notifications

- Push + e-mail + in-app notifications live in `models/notifications` (`NotificationsService`, `PushService`); the user-facing API is `account/notifications` (`api/notifications`), linked from the API root's `_links.getNotificationSettings`. The four types (`myEvents`, `submittedEvents`, `newEvents`, `newUsers`) carry Czech title, default channel and eligible roles in `schema/notification-types.ts`; a user's settings list only the types their roles allow, and per-user overrides are a `channels` enum-array (`push`/`email`/`inApp`) in `notification_settings`, stored only once changed: `[]` disables the type, a missing row or NULL means the metadata default. Selecting `push` or `email` forces `inApp` on (inlined in the controller's update route and mirrored by the settings page, which disables the forced toggle).
- The `inApp` channel writes rows into `notifications` (`Notification` entity, `userId` is `select: false`); `GET account/notifications/items` lists the user's last 100, `POST items/:notificationId/read` and `items/read-all` set `readAt` — list and read-all hang off the API root's `_links`, single-item read off each notification's. **Push payloads must use the Angular SW shape** — `{ notification: { title, body, data: { onActionClick: { default: { operation: "navigateLastFocusedOrOpen", url } } } } }` — a flat payload is silently dropped by `ngsw-worker`.
- Frontend: `/ucet/notifikace` is the feed (unread dot, click marks read and navigates the notification's `path`, mark-all + settings in header actions; item also in the sidebar and avatar popover), `/ucet/notifikace/nastaveni` the settings (channel toggles per type, device list with test/delete, "Zapnout na tomto zařízení"). `PushNotificationsService` (`core/services`, activated in `AppComponent`) owns the `localStorage.notificationsDeviceId`, subscribes via `SwPush` and on app start re-POSTs the current subscription **only if the device is still in the backend list** — re-adding one deleted elsewhere would resurrect it. `SwPush` is disabled in dev builds, so the subscribe UI degrades to "prohlížeč nepodporuje" there.
- **VAPID keys arrive at runtime** via `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` (generate with `npx web-push generate-vapid-keys`; `VAPID_SUBJECT` optional). Unset keys disable push cleanly — `pushEnabled: false`, no public key served, sends skipped — while e-mail keeps working.
- A device is a row in `notification_subscriptions`, unique per `(userId, deviceId)` where `deviceId` is a client-generated id kept in the browser. `POST account/notifications/devices` upserts by that pair, so a rotated endpoint/keys update the same row instead of duplicating the device; any other row holding the same endpoint (globally unique) is deleted first. The endpoint is a capability URL and the keys decrypt only that device's payloads, so all three are `select: false` and never leave the backend. A push send answered 404/410 deletes the subscription — that applies to `POST devices/:deviceId/test` too, which otherwise verifies the whole chain.
- Notification triggers are fire-and-forget calls from controllers (`.catch` + log, never blocking the response): event submit → `submittedEvents` to program+admin; publish → `myEvents` to the event's leaders and `newEvents` to everyone else; reject/cancel/uncancel → `myEvents` to leaders; user create → `newUsers` to admins. **The acting user is excluded**, so publishing your own event notifies you of nothing — `NOTIFY_ACTOR=true` keeps them in and makes the whole chain testable on one account (logs a warning at start; test environments only).
- **`myBugReports` notifies the reporter once the fix is in production**, and is the one trigger that fires from `main.ts` rather than a controller: the deploy job only pings Watchtower, so CI never learns when the new backend is actually up, and a plain restart or a rollback would bypass it entirely. After `app.listen()` (fire-and-forget) `ReleaseNotificationsService` reads `release-issues.json` and notifies the reporters of the issues in it. It skips silently when the file is missing (dev), when its version is not a `v*` release (NEXT builds) and — with a warning — when the version does not match `config.app.version`. `POST /feedback/bug` records a `bug_reports` row (`userId`, `repo`, `issueNumber`, `title`, unique per repo+issue, insert `orIgnore`) whose **`notifiedAt` is the only idempotence state** — no bookkeeping of released versions, so restarts and rollbacks re-send nothing. The row is written only when a GitHub issue was actually created, and a failed write is logged rather than failing the report.
- **`GET /feedback/bugs` lists the caller's own reports** — the page `/ucet/chyby`, opened from the "Moje nahlášené chyby" button in the report dialog and the target of the `myBugReports` notification. The state is derived, never stored, and **never asks GitHub** — one issue lookup per report made the page load visibly late: `release-issues.json` (or `notifiedAt`) → `released`, the row's only badge ("Opraveno", with the release version in its meta line); `open` deliberately shows none. Closing an issue therefore shows nothing until the fix ships. The row is not a link — a GitHub icon at its right opens the issue, so the rest of the line stays free. The report dialog had to become a component (`BugReportModalComponent`) to carry the second button; the sidebar and the account menu both open it through `BugReportService`.
- **`ReleaseIssuesService` (`models/bug-reports`) owns `release-issues.json`** for both readers — the bug list and `ReleaseNotificationsService`. It caches the parsed file for the life of the process, which is exactly its lifetime: the file is baked into the image and only a deploy changes it.
- **An issue only reaches `release-issues.json` if the fixing commit references it** (`Closes #123`, or `(#123)` in the subject) — the same rule as the changelog, and forgetting it silently costs the reporter both their notification and the "Opraveno" badge.

## Backend entities

- **One table, one entity mapping.** Never map a table twice (an explicit `@Entity("x")` _and_ a `@JoinTable` over `"x"`): TypeORM builds two metadata objects and **every** generated migration then drops and recreates that table's indexes — drift that survives being applied. `events_groups` is mapped **only** by the `@ManyToMany`/`@JoinTable` on `Event.groups` and must never get an entity again; code touching it directly works off the table name (`clearJoinTable()` in `mongo-import.service.ts`).
- **`Event.groupsIds` is a `@RelationId`, so it is read-only.** Writes go through the relation: `EventsRepository.updateEvent()` turns `groupsIds` into `groups` references and lets the cascading `save()` sync the join rows.
- **Files imported from the old server keep their Mongo ObjectId** in `Event.srcId` / `Photo.srcId`+`srcAlbumId` and stay in the legacy on-disk layout (folder keyed by the ObjectId, `registration.pdf`); native records use the numeric-id layout (`prihlaska_<name>.pdf`). Resolution coalesces on `srcId` — see `PhotosFilesService.getPhotoImagePath` and `EventsRegistrationsController`.

## Database migrations

- **Always** generate migrations with `npm run migrations:generate --name=<Name>` from `backend/` — never by hand, never `migrations:create`. Change the `@Column`/`@Entity` definition first (collation, type, nullable, indexes) and let the generator diff it against the DB.
- **Always read and fix up the generated migration before running it**: delete unrelated drift the diff swept in (it compares _all_ entities); add by hand what TypeORM cannot generate (`CREATE COLLATION`, extensions, text-search configs) ahead of the statement needing it — see `*-GroupNameNaturalNumericCollation.ts`; and make sure `down()` really reverses `up()`.
- **Generated columns must be registered in `typeorm_metadata`**, or every later generate drops and recreates them: pair each `ADD` with the `INSERT INTO "typeorm_metadata"` the generator emits and each `DROP` with a `DELETE`, but use `current_database()` instead of a hardcoded DB name. `*-SearchVectorColumns.ts` is the reference: it also creates the `unaccent` extension and `simple_unaccent` config, and — since TypeORM cannot express `USING gin (...)` — declares the GIN index with `@Index("…", { synchronize: false })` and creates/drops it by hand.
- **Full-text search uses stored `search_vector` tsvector columns** on members, members_contacts, events, albums and users, built with `to_tsvector('simple_unaccent', …)` (the 2-arg form is IMMUTABLE, so it is legal in a STORED column). `simple_unaccent` is `simple` with word tokens remapped through `unaccent` → case- and diacritic-insensitive. Query with `search_vector @@ to_tsquery('simple_unaccent', :q)` and build `:q` via `toPrefixTsQuery()` (`helpers/search.ts`). It matches whole words and prefixes only — not mid-word substrings (that would need `pg_trgm`).
- **Members and their contacts are also searched by phone and e-mail** (#362). The column expression normalises phones (separators between digits dropped, so `777 123 456` is one token; leading `+420`/`00420` stripped, a bare `420` kept — `4xx xxx xxx` is a real landline range) and splits e-mails with `translate(…, '@._+-', '     ')`, or the parser emits the whole address as a single token. `toPrefixTsQuery()` normalises phones the same way — **change one and you must change the other**. A generated column only sees its own row, so `MembersRepository.getMembers()` ORs the member's vector with an `EXISTS` over their contacts' vectors.
- Apply and verify rather than assume: `migrations:run`, check the schema/data, `migrations:revert` to test both directions, then `migrations:generate` once more — a clean change reports _"No changes in database schema were found"_. Migrations auto-run in production only; in dev, apply them yourself.

### Running Postgres in a cloud/sandbox session

Postgres 16 is preinstalled but **cannot run as root** — use the unprivileged `postgres` user.

```bash
PGBIN=/usr/lib/postgresql/16/bin
PGDATA=/tmp/pgdata; rm -rf "$PGDATA"; mkdir -p "$PGDATA"; chown postgres:postgres "$PGDATA" /tmp
su postgres -c "$PGBIN/initdb -D $PGDATA -U postgres --auth=trust"
su postgres -c "$PGBIN/pg_ctl -D $PGDATA -o '-p 5432 -k /tmp -c listen_addresses=127.0.0.1' -l /tmp/pg.log start"
PGPASSWORD=postgres psql -h 127.0.0.1 -U postgres -c "CREATE DATABASE interni;"
PGPASSWORD=postgres psql -h 127.0.0.1 -U postgres -c "ALTER DATABASE interni SET app.environment = 'test';"
PGPASSWORD=postgres psql -h 127.0.0.1 -U postgres -d interni -c "CREATE EXTENSION IF NOT EXISTS postgis;"
export DB_HOST=127.0.0.1 DB_PORT=5432 DB_USER=postgres DB_PASSWORD=postgres DB_DATABASE_NAME=interni DB_SCHEMA=public
cd backend && npm ci && npm run migrations:run
```

**PostGIS** (needed by `Event.placeGeometry`) is not preinstalled: if `CREATE EXTENSION postgis` fails, `apt-get update && apt-get install -y postgresql-16-postgis-3` — the `update` is required. `unaccent` ships with core.
